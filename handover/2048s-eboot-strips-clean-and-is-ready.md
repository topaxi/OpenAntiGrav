# 2048's eboot strips clean and is ready to import; nothing has been named in it yet

2026-08-26, branch `worktree-2048-vita-decrypt`. All seven of WipEout 2048's PKGs (USA + EUR base, patch v1.04, DLC1/DLC2) are decrypted end to end: `pkg2zip -x` strips the outer AES-CTR layer, `scripts/build-psvpfstools.sh`'s `psvpfsparser` strips the PFS layer given a zRIF, and the result is a real ARM ELF32 - verified with `readelf`, not assumed. Base and patch `eboot.bin` are genuinely different binaries (different SHA-256, different size, patch splits `data.psarc` into `data1.psarc`+`data2.psarc`), so they need separate treatment, not one shared name.

**What Ghidra needs that the decrypted `eboot.bin` still doesn't have**: it opens with an SCE self header, and VitaLoaderRedux's loader (`ArmElfPrxLoader.findSupportedLoadSpecs`, read directly rather than assumed) parses a plain ELF header from byte 0 with no SCE-magic handling at all - so it cannot open a SELF, only the ELF inside it. `scripts/strip-vita-self.py` does that one step, parsing the real `SCE_header` struct (matched against CelesteBlue-dev/PSVita-RE-tools's `vita-unmake-fself`) rather than hardcoding the `elf_offset` it happened to find (0xa0, same across every file checked - eboot and every `sce_module/*.suprx`, base and patch, both regions). `just strip-vita-self <path>` writes `<name>.elf` beside the input; run it on `data/extracted/vita/{PCSF00007,PCSA00015}/patch-v104/eboot.bin`, the two that matter (the patch content is what a real device would actually run - same precedent as `pulse-psp-eu` being kept as reference, not the played-from target). Both patch and base `eboot.elf` are already sitting there from this session's run.

**Key material lives in `data/keys/`** (gitignored, see its own README): `vita-zrif.tsv` has every zRIF recovered so far (2 from nopaystation.com's own TSV export via WebFetch, which is unreliable for a specific row in a large file - see the two others that came from the user pasting the site's own search result directly); `vita-f00d-cache.tsv` has the derived klicensee/encrypted-key pairs so a re-decrypt needs neither network nor the third-party `cma.henkaku.xyz` service. Two of `data/`'s original `.rap` files (from a bulk NoPayStation-style dump) were deleted rather than kept: `2048-vita-eu.rap` proved wrong for that exact pkg (`header signature is invalid`, confirmed against the working zRIF), and the USA DLC2 `.rap` has no matching pkg on hand.

## Open

- No zRIF for `UP9000-PCSA00015_00-DLC2W2048PACKAGE` pairs with a pkg on hand (have the zRIF, not the file) or vice versa for the network pass content ID - neither blocks anything currently planned.
- DLC PKGs carry no binaries at all (`dlcN.psarc` + `sce_sys` metadata only, checked directly against the decrypted tree) - there is nothing in them for Ghidra either way.
