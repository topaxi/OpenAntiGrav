# Every SFX trigger is a Pulse reading, applied to Pure and HD on a bet

Split out 2026-09-02 from `hds-bnk-sound-banks-read-and-hd-makes.md`, whose own scope (the `.bnk` container format and both waveform codecs) is now fully resolved and closed. This caveat was carried in that thread's opening paragraph but was never actually part of its `## Next Steps`, and it is not really about bank *decoding* at all - it is about the nine [`oag_game::audio::sfx::Cue`](../crates/game/src/audio/sfx.rs) variants, each of whose trigger (`SpeedupPad`, `Collision`, `Absorb`, `Engine`, `Shield`, `ShieldActive`, `Disengaging`, `Blowup`, `LockOn`) was recovered from **Wipeout Pulse's PSP executable only**. `crates/game/src/audio/sfx.rs`'s own module doc already states this plainly: *"no Pure or HD dispatch has ever been looked at. Firing a Pulse-recovered edge on those titles is a bet ... Reasonable, and not a reading; confidence 50."* That confidence-50 line is the reason this is worth its own thread: it is below this project's naming and trust threshold on two of the three titles this engine plays, for every single wired sound effect.

## Open

- Whether Pure's executable calls the same `Sound_Play`/`Sound_PlayLooping` sites at the same simulation edges Pulse does, for the remaining **one** cue, `Blowup` - all eight others are now confirmed (2026-09-04, see `docs/ghidra/functions/psp-pure-usa/rocket-and-collision-fx.md`, `shield-sound.md`, `dry-play-cues.md`, `exhaust-sound.md` and `lockon-sound.md`).
- Whether Wipeout HD's PS3 executable does the same, for all nine cues. HD's `ShipCollisionFx_Trigger`, `Exhaust_UpdateEngineSound`, `Shield_Activate` and so on are presumably different functions at different addresses in a different binary (PPC64, per-function TOC defect - see `docs/ghidra/functions/ps3-hdfury-eu/memory.md`), not yet located.
- Whether the *gating* logic matches, not just the call site's existence - confirmed for `Collision` and `Absorb` on Pure (same cooldown/stagger shape, one real difference found: `Absorb`'s stagger loop runs 8 times on Pure against Pulse's 10); confirmed for `Shield`/`ShieldActive`'s **call order and cue names**, but Pure's `shieldactive` call reads unconditional where Pulse's is gated on a field `shield-sound.md` didn't chase; confirmed the same shared dry-play chain (now identified end to end, `Scream_PlaySoundByName` on both sides) fires `SpeedupPad` and `Disengaging`, but `Disengaging`'s own countdown threshold on Pure is unread (`dry-play-cues.md`); `Engine`'s voice-open edge confirmed with two exactly-matching tuning constants (`-1143.0`, `0.01`), but its per-tick pitch/volume write is unchecked (`exhaust-sound.md`); `LockOn` confirmed near line-for-line, including the shared choice to bypass the gate helper (`lockon-sound.md`). Still fully open for `Blowup` and for HD entirely.
- **`Blowup` did not turn up among the dry-play chain's nine gate-helper call sites** (`dry-play-cues.md`) - resolved for `LockOn` (it bypasses the gate helper and calls the chain's middle hop directly, `lockon-sound.md`), so `Blowup` likely does the same. Its Pure call site is still unfound.

## Next Steps

- **`Blowup` is the last Pure cue.** Two options, cheapest first: (1) `Ship_SetState`'s case-4 equivalent (Pulse: `0x0884430c`, reached through a nine-entry jump table) may be findable the same way `LockOn` was - `search_strings("~BLOWUP")` on Pure, then a `lui`/`addiu` backward search on the derived offset, since `LockOn` showed this cue family often builds its string directly rather than through the gate-helper chain. (2) If that comes up empty, fall back to the jump-table structure itself: find Pure's nine-entry `Ship_SetState`-equivalent state dispatcher and read its case 4 directly, the way Pulse's own reading did.
- All eight confirmed cues' corroboration is decompilation-only (confidence 78-82, capped by the `85`+ band needing a runtime trace); a PPSSPP capture of any of the Pure trigger functions named across `rocket-and-collision-fx.md`, `shield-sound.md`, `dry-play-cues.md`, `exhaust-sound.md` and `lockon-sound.md`, the way `docs/reverse-engineering/ppsspp-debugger.md` already does for Pulse, would raise them past that ceiling if anyone picks this thread up for verification instead of coverage.
- `oag-wad sounds <archive>` lists the cues each bank actually carries per title, useful for confirming a candidate cue name exists on Pure/HD before spending time hunting its trigger - this is how all eight confirmed cues' names were checked present in Pure's banks before the Ghidra read.
- **`search_strings` on a candidate address first, arithmetic and `jal`-wart search second.** Every cue found this session started from `search_strings` locating the literal cue name directly in Ghidra's own string index, then worked backward to the code that references it (`operand_pattern` on the derived offset) - faster and self-verifying, versus starting from a caller search and hoping to recognise the right string once decompiled. `~ENGINE` and `~ROCKLOCK` were both found this way in under ten tool calls each.
- **Before writing "X is a flat/simple/one-hop Y", grep `sfx.rs` and every doc page that already cites the function.** A same-session pass wrote that claim about Pulse's dry-play helper without checking what it actually calls, and had to correct it once `Disengaging`'s own citation (`FUN_0883e9b0` -> `FUN_0893a768`) was reread - a claim already on record beats a fresh read of one call site. Separately, a spawn-helper address was first computed wrong (`0x0886de1c` instead of `0x08871e1c`, a `0x4000` slip), caught only by decompiling the candidate and comparing it structurally against the Pulse function it claimed to match - "is a function entry" alone did not catch it.
- **Once `Blowup` is confirmed, close this thread's Pure half and consider it a natural stopping point** - reevaluate whether the same session continues into HD (a different binary, a different toolchain trap, the `0x32d5e0` TOC break) or hands off. Nine of nine on Pure is a coherent unit; starting HD cold in the same sitting risks the coverage-over-verification trade this thread's own Next Steps already warns about.
- HD's PPC64/TOC binary is still the harder half and can follow once more of the PSP-side pattern (Pure vs Pulse) is established, or be picked up independently.
