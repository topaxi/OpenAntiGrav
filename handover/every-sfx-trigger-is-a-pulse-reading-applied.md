# Every SFX trigger is a Pulse reading, applied to Pure and HD on a bet

Split out 2026-09-02 from `hds-bnk-sound-banks-read-and-hd-makes.md`, whose own scope (the `.bnk` container format and both waveform codecs) is now fully resolved and closed. This caveat was carried in that thread's opening paragraph but was never actually part of its `## Next Steps`, and it is not really about bank *decoding* at all - it is about the nine [`oag_game::audio::sfx::Cue`](../crates/game/src/audio/sfx.rs) variants, each of whose trigger (`SpeedupPad`, `Collision`, `Absorb`, `Engine`, `Shield`, `ShieldActive`, `Disengaging`, `Blowup`, `LockOn`) was recovered from **Wipeout Pulse's PSP executable only**. `crates/game/src/audio/sfx.rs`'s own module doc already states this plainly: *"no Pure or HD dispatch has ever been looked at. Firing a Pulse-recovered edge on those titles is a bet ... Reasonable, and not a reading; confidence 50."* That confidence-50 line is the reason this is worth its own thread: it is below this project's naming and trust threshold on two of the three titles this engine plays, for every single wired sound effect.

## Open

- Whether Pure's executable calls the same `Sound_Play`/`Sound_PlayLooping` sites at the same simulation edges Pulse does, for the remaining **three** cues (`Engine`, `Blowup`, `LockOn`) - `Collision`, `Absorb`, `Shield`, `ShieldActive`, `SpeedupPad` and `Disengaging` are now confirmed (2026-09-04, see `docs/ghidra/functions/psp-pure-usa/rocket-and-collision-fx.md`, `shield-sound.md` and `dry-play-cues.md`).
- Whether Wipeout HD's PS3 executable does the same, for all nine cues. HD's `ShipCollisionFx_Trigger`, `Exhaust_UpdateEngineSound`, `Shield_Activate` and so on are presumably different functions at different addresses in a different binary (PPC64, per-function TOC defect - see `docs/ghidra/functions/ps3-hdfury-eu/memory.md`), not yet located.
- Whether the *gating* logic matches, not just the call site's existence - confirmed for `Collision` and `Absorb` on Pure (same cooldown/stagger shape, one real difference found: `Absorb`'s stagger loop runs 8 times on Pure against Pulse's 10); confirmed for `Shield`/`ShieldActive`'s **call order and cue names**, but Pure's `shieldactive` call reads unconditional where Pulse's is gated on a field `shield-sound.md` didn't chase; confirmed the same shared dry-play chain (now identified end to end, `Scream_PlaySoundByName` on both sides) fires `SpeedupPad` and `Disengaging`, but `Disengaging`'s own countdown threshold on Pure is unread (`dry-play-cues.md`). Still fully open for `Engine`, `Blowup`, `LockOn` and for HD entirely.
- **`Blowup` and `LockOn` did not turn up among the dry-play chain's nine call sites** (`dry-play-cues.md`) despite Pulse routing both `Blowup` (`Ship_SetState` case 4) and, per `sfx.rs`, a dry no-emitter shape through the same family of helper. Either their Pure call sites use a `jal`-wart pseudo-target this pass didn't search for, or Pure's implementation genuinely diverges here - not yet distinguished.

## Next Steps

- Pick the next cue - `Blowup` and `LockOn` are what's left of the "dry, no-emitter" family; `Engine` is structurally different (a per-tick pitch/volume write via `Exhaust_UpdateEngineSound`, not a one-shot trigger) and may be cheaper to chase by finding Pure's exhaust-update function directly rather than through the dry-play chain.
- All six confirmed cues' corroboration is decompilation-only (confidence 78-82, capped by the `85`+ band needing a runtime trace); a PPSSPP capture of any of the six Pure trigger functions named across `rocket-and-collision-fx.md`, `shield-sound.md` and `dry-play-cues.md`, the way `docs/reverse-engineering/ppsspp-debugger.md` already does for Pulse, would raise them past that ceiling if anyone picks this thread up for verification instead of coverage.
- `oag-wad sounds <archive>` lists the cues each bank actually carries per title, useful for confirming a candidate cue name exists on Pure/HD before spending time hunting its trigger - this is how all six confirmed cues' names were checked present in Pure's banks before the Ghidra read.
- **Corroborate a `jal`-wart or string-wart arithmetic result against Ghidra's own index before trusting it, not just against `get_function_by_address`.** A same-session pass first computed the shared spawn helper's real address wrong (`0x0886de1c` instead of `0x08871e1c`, a `0x4000` slip), caught only by decompiling the candidate and comparing it structurally against the Pulse function it claimed to match (`Psys_Spawn_q`) - "is a function entry" alone did not catch it. The same session separately wrote down that "Pulse's dry-play helper is a flat one-hop call" without checking what it actually calls, and had to correct that too once `Disengaging`'s own citation in `sfx.rs` (`FUN_0883e9b0` -> `FUN_0893a768`) was reread. **Before writing "X is a flat/simple/one-hop Y", grep `sfx.rs` and every doc page that already cites the function - a claim already on record beats a fresh read of one call site.** `search_strings` on a candidate address, independently confirming it against Ghidra's own index rather than arithmetic alone, is the cheap check that caught nothing wrong here and should stay the default.
- HD's PPC64/TOC binary is still the harder half and can follow once more of the PSP-side pattern (Pure vs Pulse) is established, or be picked up independently.
