# Every SFX trigger is a Pulse reading, applied to Pure and HD on a bet

Split out 2026-09-02 from `hds-bnk-sound-banks-read-and-hd-makes.md`, whose own scope (the `.bnk` container format and both waveform codecs) is now fully resolved and closed. This caveat was carried in that thread's opening paragraph but was never actually part of its `## Next Steps`, and it is not really about bank *decoding* at all - it is about the nine [`oag_game::audio::sfx::Cue`](../crates/game/src/audio/sfx.rs) variants, each of whose trigger (`SpeedupPad`, `Collision`, `Absorb`, `Engine`, `Shield`, `ShieldActive`, `Disengaging`, `Blowup`, `LockOn`) was recovered from **Wipeout Pulse's PSP executable only**. `crates/game/src/audio/sfx.rs`'s own module doc already states this plainly: *"no Pure or HD dispatch has ever been looked at. Firing a Pulse-recovered edge on those titles is a bet ... Reasonable, and not a reading; confidence 50."* That confidence-50 line is the reason this is worth its own thread: it is below this project's naming and trust threshold on two of the three titles this engine plays, for every single wired sound effect.

## Open

- Whether Pure's executable calls the same `Sound_Play`/`Sound_PlayLooping` sites at the same simulation edges Pulse does, for the remaining **five** cues (`SpeedupPad`, `Engine`, `Disengaging`, `Blowup`, `LockOn`) - `Collision`, `Absorb`, `Shield` and `ShieldActive` are now confirmed (2026-09-04, see `docs/ghidra/functions/psp-pure-usa/rocket-and-collision-fx.md` and `shield-sound.md`).
- Whether Wipeout HD's PS3 executable does the same, for all nine cues. HD's `ShipCollisionFx_Trigger`, `Exhaust_UpdateEngineSound`, `Shield_Activate` and so on are presumably different functions at different addresses in a different binary (PPC64, per-function TOC defect - see `docs/ghidra/functions/ps3-hdfury-eu/memory.md`), not yet located.
- Whether the *gating* logic matches, not just the call site's existence - confirmed for `Collision` and `Absorb` on Pure (same cooldown/stagger shape, one real difference found: `Absorb`'s stagger loop runs 8 times on Pure against Pulse's 10); confirmed for `Shield`/`ShieldActive`'s **call order and cue names**, but Pure's `shieldactive` call reads unconditional where Pulse's is gated on a field `shield-sound.md` didn't chase - open whether Pure has an equivalent gate elsewhere. Still fully open for the other five cues and for HD entirely.
- **Pure's low-level SCREAM dispatch path** (`func_0x001209e0` -> `func_0x0002c8f0` -> `func_0x00031a90`, `shield-sound.md`) looks like a "play by bank+index" primitive sitting under the by-name `Sound_Play` wrapper, structurally distinct from Pulse's flat one-hop dry-play helper - not chased past confirming it looks like sound-engine code (an `"SBlk"` magic check, a SCREAM-shaped error path). Whether it is genuinely a deeper equivalent of Pulse's `FUN_0883e9b0` or a different mechanism entirely is open.

## Next Steps

- Pick the next cue - work down the `Cue` list in `crates/game/src/audio/sfx.rs` in whatever order the module doc's citations make cheapest to chase. `Blowup` is a reasonable next target since Pulse's own trigger (`Ship_SetState` case 4 -> `FUN_0883e9b0`) shares the same dry-play helper `ShieldActive` used, so `shield-sound.md`'s open SCREAM-chain question may resolve as a side effect of chasing it.
- The four confirmed cues' corroboration is all decompilation-only (confidence 80-82, capped by the `85`+ band needing a runtime trace); a PPSSPP capture of any of `ShipCollisionFx_Trigger`, `FUN_08925e20` or `FUN_0892425c` on Pure, the way `docs/reverse-engineering/ppsspp-debugger.md` already does for Pulse, would raise them past that ceiling if anyone picks this thread up for verification instead of coverage.
- `oag-wad sounds <archive>` lists the cues each bank actually carries per title, useful for confirming a candidate cue name exists on Pure/HD before spending time hunting its trigger - this is how all four confirmed cues' names were checked present in Pure's banks before the Ghidra read.
- **Corroborate a `jal`-wart or string-wart arithmetic result against Ghidra's own index before trusting it, not just against `get_function_by_address`.** A same-session pass first computed the shared spawn helper's real address wrong (`0x0886de1c` instead of `0x08871e1c`, a `0x4000` slip), caught only by decompiling the candidate and comparing it structurally against the Pulse function it claimed to match (`Psys_Spawn_q`) - "is a function entry" alone did not catch it. `shield-sound.md`'s string reads used the stronger check throughout: `search_strings` on the candidate address independently confirms it, cheaper than a structural comparison and catchable before committing anything.
- HD's PPC64/TOC binary is still the harder half and can follow once more of the PSP-side pattern (Pure vs Pulse) is established, or be picked up independently.
