# A circuit's billboard slots are a 9-entry array on the engine side, and slot 7 is not what it says it is

2026-08-25, mechanism read at instruction level (capped 84, static-only per [visibility.md](../../docs/ghidra/functions/ps3-hdfury-eu/visibility.md)'s own rule). Full account: [billboards.md](../../docs/ghidra/functions/ps3-hdfury-eu/billboards.md). `TrackStartup_Load` (`0x000b19a8`, `Track.cpp`) parses `Num`/`Location`/`Color`/`Colour`/`Glow` per `<Billboard>` and stores each into a singleton's array at literally `array[Num]`, 1-8, index 0 wasted - confirmed two ways: `Billboard_CreateFromLocation_q`/`_FromColour_q` (`0x0029adf8`/`0x0029af88`) index it unadjusted, and its manager's constructor/destructor pair zeroes exactly nine words, matching the manifest's own comment, `"num" (1-8)`. **That kills "a node looked up by a name the engine builds"**: the two stray `Billboard<digits>` nodes on `02_track`/`05_ubermall` are artist debris. It **instantiates** rather than merely texturing existing geometry - `Billboard_ConstructResource_q` (`0x0029a6a8`) branches on the location's own `.vex`/`.mip` suffix and allocates a 0x2080- or 0x100-byte object; no manifest on the disc names a non-`.vex` location, so the `.mip` arm is implemented-and-unexercised, the same shape as the draw-order row's `0x31` branch. `type` is read nowhere in this function despite every one of 118 slots authoring it - unconsumed here, unread elsewhere. Checked against all 16 extracted manifests: none authors `Colour`, `Glow` or `<Render>`, so the parser is right to skip them; `<Render>` is a `<Billboard>` sibling this function recognises by name and then discards the comparison result outright - dead code in this build. **The new, surprising part**: `Billboard_CreateFromLocation_q` special-cases `Num==7`, not 8, and replaces whatever the manifest authored there (always `fx350.vex`, all 16 circuits) with a pointer read off a global mode-descriptor struct, when two of its fields are non-null. Four `321Go_*.vex` names (`StartFinish`/`Zone`/`HD_Zone_Battle`/`hd_detonator`) sit in the same TOC window and match the four known race-gate shapes by name, but the pointer was not traced all the way to one of them - a lead, not a finding. **Chased, partially**: `GetBillboardMeshIdFromName` still has no found caller - its only xref is a data reference into the module's ordinary `.opd` section, not a billboard-specific table as first thought (checked both sides: the descriptor pattern runs on well past any table-sized window). A separate, unnamed 4.5 KB function (confidence below 50) *is* reached for real, traced from `Billboard_ConstructResource_q` through a TOC trampoline, and inlines the same search-and-bind write against a same-shaped per-slot lookup: a repeated bind idiom, still resetting rather than positioning. If a caller exists it must use a 0-based index, not raw `Num`. No direct `bl` caller and no stored function pointer (validated against a control) - no known invocation path, not confirmed dead. Nothing placed.

2026-08-28, cross-title: **Pulse ships the same file, per circuit, and the parser silently found nothing on it until now.** `TrackStartup::parse` (`oag_tables::trackstartup`) called `fexml::parse` directly; that reads HD's plain XML fine but returns zero billboards on Pulse's `fexml`-shortened one, which needs `fexml::text` run first to expand the `<code>` dictionary - fixed, with a regression fixture. A second, independent bug in `oag-game`'s load report (`crates/raceplay/src/load.rs`) looked for `/` to find a circuit's directory, which finds nothing on Pulse's `\`-joined paths even once the parser is fixed - also fixed, and both are covered by a new ground-truth test (`pulses_default_track_reports_its_own_trackstartup_xml`) and a real-disc `--dry-run` run against `16_Track`. Read directly off 11 of Pulse's 12 circuits (`26_Track` is `25_Track`'s `Zone` variant and carries no manifest of its own): **slot 8 is `321Go_StartFinish.vex` on every circuit that authors one billboard 8**, the same as HD - except `14_Track`, which authors *three* entries under `num="8"` (`Checkered_StartFinish.vex`, `Final_Lap_StartFinish.vex`, `321Go_StartFinish.vex`); `TrackStartup::billboard` returns the first, and which one the original shows when is unread. **"Slots 7 and 8 are reserved" does not generalise**: Pulse's slot 7 is a different model or colour on nearly every circuit, never `fx350.vex` (that name is HD-only, not on any Pulse manifest). Full table in `oag_tables::trackstartup`'s own "Cross-title: Pulse" doc section.

Also found while reading Pulse's disc for this: `Data\Plugins\PI004\Definition.xml`, a 35-entry catalogue of every billboard advert on the disc - name, `Portrait`/`Landscape`, `location`, and a space-separated list of colours the model supports. Every colour name any `TrackStartup.xml` authors also tags a `PI004` entry, which reframes a colour fill as a **pool selector** into this catalogue rather than a literal tint - plausible, not confirmed, since nothing has traced a function reading either side of it. `docs/formats/pure-status.md` independently found the same plugin id on Pure (excluded from the language picker, never read for content before now), so this is very likely a third title, not just Pulse.

**A cheap placement hypothesis was tried and killed, on purpose, before it reached the renderer.** `16_Track`'s own art mesh embeds five numbered placeholder textures (`billboard1/2/6/7/8.tga`, each an 8x8 icon of its own digit) on a handful of quads scattered through the track - see `docs/formats/vex.md`'s texture-stride section for how those were first found, and CLAUDE.md's "billboards by default just render an actual number" is that texture, seen live in this project's own renderer, not the original. Binding each slot to the placeholder quad wearing its number, using the quad's own world transform (`oag_vex::vex::world_transforms`, already available), was the obvious next move - and the manifest itself rules it out: `16_Track` authors all eight slots but only five numbers have a matching placeholder texture anywhere in the mesh. A mechanism that cannot place three of the eight slots it is supposed to explain is not the mechanism, so nothing was wired off it - the same shape of trap the `Billboard<digits>` node names above turned out to be.

2026-08-28, later the same day, **live PPSSPP trace: Pulse's own loader found, and "nothing is placed" is now a runtime-confirmed fact rather than a static inference.** Full account: `docs/ghidra/functions/psp-pulse-usa/billboards.md`. A halting read watchpoint on `%s\TrackStartup.xml` fired mid-circuit-load; walked live via exec breakpoints on each callee's `jr ra` (a stack-offset guess for one caller's return address gave a plausible but wrong value once - the breakpoint technique is the one to trust). The chain: `World_LoadTrack` -> `Xml_OpenFile` -> `TrackStartup_Parse` (`0x08884ac4`, reads the same six attributes this project's `oag_tables::trackstartup` does, `Color`/`Colour` merging confirmed live) -> `Billboard_CreateFromLocation_q`/`Billboard_CreateFromColour_q` (`0x089012d4`/`0x08901004`, both index a 9-entry array by raw `num`, same architecture as HD's) -> `Billboard_ConstructResource_q` (`0x08900220`, same `.vex`/`.mip` dual-branch, dual-size architecture as HD's `Billboard_ConstructResource_q`). **The shared constructor writes a 4x4 transform into every new billboard, and read live it is the literal identity matrix - the same sixteen floats regardless of `num`.** `num` only indexes the array and seeds three derived resource-tag IDs, never a position. All four functions renamed (`TrackStartup_Parse` 78, `Billboard_ConstructResource` 75, the two constructors 65/60 with `_q`) and added to `names.tsv`.

**One live lead survives, and it beats every HD-side lead on offer**: `Billboard_CreateFromColour_q` walks a per-track pool (`*(int*)(_DAT_002ae2b4+0x3c)`, count at `+0x40`) before constructing anything, matching entries by type hash and a colour bitmask, consuming the match. Confirmed *reached* during a real circuit load - not merely referenced, the failure mode `GetBillboardMeshIdFromName` on HD and `PI004` on Pulse both have. Its entries' own layout (what sits at their `+0x94` and neighbours) was not read; this, not `PI004`'s catalogue, is now the best next step if placement is chased further.

A second, unrelated trap surfaced walking the call chain: several call targets in `Billboard_ConstructResource` decompile as `func_0x00XXXXXX(...)`, a low pseudo-address `get_function_by_address` cannot resolve even though `docs/ghidra/workflow.md` records this binary's *data*-constant relocation wart as fixed. `real = pseudo + 0x08804000` (the binary's own image base) held for every case checked - reads as the `R_MIPS_26` (`jal` target) relocation not being applied even where `R_MIPS_HI16`/`R_MIPS_LO16` are. Noted in `workflow.md` itself; not chased further at the time. (Resolved 2026-09-07, see the Open list below.)

2026-08-28, corrected the same day: **"construction places nothing" was misread as "nothing overrides the disc's texture", and that was wrong.** Caught by the project owner, who plays the original and said the start-line gantry never shows a stretched digit - checked directly rather than argued past: a live screenshot of the original's `16_Track` start line shows a "GO" board, never `billboard8.tga`'s digit, matching a screenshot the owner supplied of this project's own renderer showing exactly that digit stretched over signage elsewhere on the same lap. Full account, including a corrected verdict: `docs/ghidra/functions/psp-pulse-usa/billboards.md`. In short: `num`'s three derived tags are lookup keys into a **shared registry** all eight billboard slots register into (found by scanning RAM for the literal tag values - slot 8's three cluster together, slot 7's sit immediately adjacent, same table). The two objects slot 8's tags resolve to are read constantly through a real countdown-to-green cycle (12k+ and 7k+ watchpoint hits over ~44 s, against a live control), not once at construction; one carries a live per-frame animation-time accumulator and four candidate display-state pointers - the right shape for a multi-frame countdown. The final texture bind for that screen position was not caught in the act, so this is strong circumstantial evidence, not an instruction-level proof. Corrected in `crates/tables/src/trackstartup.rs`'s own doc comment too, which carried the same overclaim.

**The lesson, stated plainly for the next time this shape of mistake is tempting**: "the constructor doesn't compute a transform" and "nothing downstream of construction changes what's drawn" are different claims, and only the first was checked before the second was asserted as a verdict. A player's own observation of the original is what caught it - a screenshot comparison would have caught it just as fast, and costs one PPSSPP launch. Worth doing before publishing a negative result on any "the disc's own asset is what plays" question, not after.

2026-08-28, a third pass, chasing the texture bind itself: **it's a separate instantiated mesh, not a retextured node 74.** The actual `Gfx_BindTexture` catch was not made (see the trap below), but a RAM scan for the literal bytes `321Go_StartFinish` during a live race found the asset's own scene graph fully resident and parsed - `VEXX` header, real node names (`world`, `camera1`, `start_lights`, `start_light_background`), the Maya build path baked into the compiled asset. This is the same `.vex` `TrackStartup.xml` names as slot 8's `location` on every circuit that authors one, confirming HD's own "instantiates rather than retextures" reading a second way. Node 74's `billboard8.tga` quad reads as authored debris the real gantry covers. **The open tension that matters most now**: the constructor's identity transform and this asset being shared across all 16 circuits mean something still has to move it to each circuit's own gantry, and that transform writer is not found - "instantiated" is settled, "drawn at the gantry" is strong inference (the asset's own `start_lights` node name fits), not caught directly. The material object's liveness was reconfirmed with a non-halting watchpoint (53,065 hits on its header over one countdown cycle, healthy 381,086-hit control); a separate sample of its four wrapper sub-objects, taken mid-race rather than during the countdown, found stale front-end credits text - almost certainly heap reuse, not real content, flagged rather than resolved. Full account: `docs/ghidra/functions/psp-pulse-usa/billboards.md`.

**A new, generalisable trap, now in `ppsspp-debugger.md`**: a halting execution breakpoint on a function called every frame (here, `Gfx_BindTexture`) silently voids a timed capture rather than producing a clean negative. 22 real seconds of capture covered roughly 0.3-0.5 s of actual game time - each halt costs ~44 ms and freezes game time completely while halted - so a plausible-looking, fully-saturated "nothing else binds here" result was actually a stalled capture that never reached the window it meant to observe. Watch the object a hot function touches with a non-halting watchpoint instead of halting on the function itself.

2026-09-02, a small corroboration from the race-start countdown thread, not a new trace: **the four `321Go_*.vex` race-gate shapes are confirmed as real, distinct geometry, not aliases or debris - by listing the actual PSARC archive rather than reading strings out of the executable.** `python3 scripts/psarc.py list data/images/hdfury-ps3-eu-dec.iso` finds all four under `/data/billboards/hd_adverts/321go/` with four different byte sizes: `321go_startfinish.vex` 12,544 B, `321go_zone.vex` 8,368 B, `321go_hd_zone_battle.vex` 10,304 B, `321go_hd_detonator.vex` 11,568 B - each also has its own matching `.rcsmodel`. Different sizes rule out four names resolving to one shared file, which this thread's own reading never fully closed. Full write-up, including the separate finding that the on-screen HUD "GO" overlay (a different object entirely, not this gantry) is identical across every mode on Pulse, Pure and HD, in [race-start-countdown-and-launch-boost.md](../gameplay/race-start-countdown-and-launch-boost.md) and [docs/ui/hud.md](../../docs/ui/hud.md#deferred-and-known).

**A second, real negative from the same pass, and it narrows the search rather than just corroborating it: the swap is not manifest-driven, on any of the four dedicated Zone environments.** HD ships `zone_1` through `zone_4` as their own environments, each with its own `trackstartup.xml` (`/data/environments/zone_<N>/trackstartup.xml`, `DATA00.PSARC`) distinct from every circuit's. Read all four directly: **every one authors `num="7"` as `fx350.vex` and `num="8"` as `321Go_StartFinish.vex` - identical to `talons_junction` and every circuit checked, byte for byte on those two lines.** So whatever picks Zone's own `321Go_Zone.vex` over `321Go_StartFinish.vex` cannot be reading the manifest differently for a Zone environment - the manifest gives it nothing to work with. That rules out "a Zone-flavoured `trackstartup.xml`" as a hypothesis outright and confirms the mechanism has to be the runtime mode-descriptor pointer this thread already suspects for `Num==7` (not `Num==8`, which every file checked authors identically and never swaps) - narrows the open item below rather than closing it.

**A third, later on the same day: the project owner confirmed from actually playing Zone, matching the asset content exactly.** "It's the text on the gantry/billboard, or lack thereof, in a zone race, it draws a small rectangular track, instead of the 3 2 1 GO." `oag-view` rendering `321go_zone.vex` straight off the disc (`data/images/hdfury-ps3-eu-dec.iso:PS3_GAME/USRDIR/DATA02.PSARC`, `--mesh /data/billboards/hd_adverts/321go/321go_zone.vex`) shows exactly that: a small flat rectangular panel, one content node (`pasted__Go_HD_start_light_321go`), carrying a 2048x1024 texture (`321_go_zone.gtf`) that renders as a stylised red/green/blue track-loop icon - 3 nodes and 222 triangles against `321go_startfinish.vex`'s 19 nodes and 1,530. Full account and both renders in [billboards.md](../../docs/ghidra/functions/ps3-hdfury-eu/billboards.md#the-four-321go_vex-shapes-are-confirmed-as-genuinely-different-content-by-rendering-them). **This raises the stakes on the mode-descriptor pointer above without touching it**: the asset-content question this thread's "a lead, not a finding" always hedged on is now about as settled as a render can settle it: whatever the runtime mechanism turns out to be, it is picking between four meaningfully different, now-confirmed pieces of content, not placeholder debris.

2026-10-06, billboards lane: **the transform question is closed by retiring it - an advert is drawn through its own camera into a 128 x 128 texture, and the track's `billboardN.tga` quad shows it.** A live PPSSPP GE dump (Talon's Junction, start line) holds two offscreen passes into `0x04154000` (width `0x80`, viewport 128 x 128) and two track prims that sample it; their vertex boxes are `16_Track`'s node 453 (`billboard7.tga`, slot 7 = Auricom) and node 74 (`billboard8.tga`, the gantry). The passes' view matrix is the inverse of the advert's `camera1`, and the projection is the `Camera` node's own: x scale `1/tan(fov/2)` with `fov` the u16 at payload `+0x22` times `180/65535` (horizontal), y scale `aspect` (payload `+0x1c`) times that - 1.857/3.714 for Auricom, 1.667/6.667 for 321Go, all four numbers with no free parameter. So the constructor's "identity matrix" is the camera's cached view matrix, and the earlier "transform writer" hunt had no object. **Drawn on Pulse PSP and PS2** (`oag_raceplay::adverts`), compared against the original at the same tick; the `N billboard-slot placeholder draw(s) suppressed` WARN is gone on Talon's Junction and stays, correctly, for a colour slot that has a quad (`05_Track`: three). Full account: [billboards.md](../../docs/ghidra/functions/psp-pulse-usa/billboards.md), 2026-10-06 section. HD: `Billboard_LoadModelAndBind` (`0x003a4da0`) builds a render target for the slot too and rebinds the `billboard%d` material's texture to it, so the mechanism very likely carries over; projection and size on HD are unmeasured and nothing is drawn there.

## Open

- **Colour slots.** `Billboard_CreateFromColour` (`0x08901004`) walks a per-track pool (`+0x3c` list, count `+0x40`; entry `+0xa0` type hash, `+0xa4` colour mask, `+0x94` model name), takes the first match and swaps it to the end of the list - no random draw in the code read. The pool's *filling* order is unread, so a colour slot is drawn nothing and the WARN stays for it.
- **The advert's animation clock** is the scenery clock (`world.tick / 60`), chosen, not measured. The captured pass shows every letter at its rest pose, which the authored loop (600 frames, 10.0 s) visits several times, so the dump does not pin it. A fit from further dumps taken at known emulated times was tried and was inconclusive (the star nodes' poses did not match the sampled matrices); the letters-only fit needs the transit windows (about 2.0-3.0 s of each loop) to be caught.
- **HD** (see above) and **slot 8 as a texture**: pass B is the gantry model through its own camera, aspect 4.0, 61.93 degrees; `oag_raceplay::gantry` still stands the model on the measured mount (a measured, accepted placement), so slot 8 does not use the card path.
- **PS2** is carried over by analogy (same camera nodes, same quads); no PCSX2 capture.
- The instruction that makes the quad's texture the card's target was not caught (two live instances agree with the by-name reading; HD builds `"billboard" + num`).
- The mode-descriptor pointer replacing `Num==7`'s mesh was not traced all the way to one of the four `321Go_*.vex` race-gate shapes (HD).
- `GetBillboardMeshIdFromName` still has no found caller (re-run 2026-09-15 after the lvlx reimport: three routes, positive control on each).
- `type` is authored by every one of 118 slots but is read nowhere in `TrackStartup_Load`; the camera's aspect (0.5 on the portrait adverts, 2.0 on landscape) is what the portrait/landscape split means for drawing.
- ~~The unnamed 4.5 KB bind function has no confirmed caller~~ **Wrong**: `billboards.md`'s 2026-09-06 section traces it (`Billboard_LoadModelAndBind`, `0x003a4da0`, 80).
- ~~`14_Track`'s three `num="8"` billboards~~ **Closed 2026-09-05**: it authors one.
- ~~No transform writer has been found~~ **Closed 2026-10-06**: there is no transform; see above.
