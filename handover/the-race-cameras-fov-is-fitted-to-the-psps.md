# The race camera's FOV is fitted to the PSP's own aspect on every title, and the PS2's own in-game widening option has no counterpart

2026-09-03, found while chasing an apparent PS2-engine-flare size mismatch that turned out to be something else (see [The PS2's engine flare plays and reads as nothing on screen](the-ps2s-engine-flare-plays-and-reads-as.md)). Not a bug in the sense of contradicting a closed reading - `race::AUTHORED_ASPECT` was already closed once, deliberately, as "right whatever the disc" for the 2D/HUD/loading-screen layout math ([`ps2-front-end-layout-is-hardcoded-to-480x272.md`](ps2-front-end-layout-is-hardcoded-to-480x272.md), 2026-08-09/08-23). This is a narrower, still-open question that closure never asked: **should the in-race 3D camera also reproduce the PS2 disc's own runtime `Aspect Ratio` option**, and today it does not, on any title.

**What's confirmed, by source:**

- `crates/game/src/frontend/space.rs:41` - `pub const SCREEN: (f32, f32) = (480.0, 272.0)`, a single global constant.
- `crates/game/src/race.rs:246` - `pub const AUTHORED_ASPECT: f32 = crate::frontend::SCREEN.0 / crate::frontend::SCREEN.1`, fed straight from it.
- `crates/game/src/race/camera.rs`'s `projection()` fits every view's vertical FOV to `AUTHORED_ASPECT` via `oag_render::camera::fit_vertical_fov`, for **every title** - PSP, PS2, Pure, HD/Fury alike. The function's own doc comment is explicit that this is deliberate: `<ExternalCameraFar fov>` "is also authored for **one** viewport shape, the PSP's own, which is the only one the original ever renders into" (confidence 94, verified live against `g_camera_fov_degrees`) - but that confidence is about the *angle*, not about whether the PS2 disc reuses it unwidened at every setting, which was never separately checked.
- This project's own `--aspect psp|ps2|free` flag (`crate::display::Aspect`) is a **different** mechanism: it shapes the letterboxed **viewport** inside the window (`display::viewport`), which then feeds `fit_vertical_fov` as the `aspect` parameter - so choosing `ps2` (4:3) does change the fitted FOV, but by "constrain the presentation rectangle and fit the authored horizontal field into it," not by "multiply the camera's own aspect by 4/3," which is what the disc's option actually does (`docs/ps2/aspect-ratio.md`, confidence 95: "Setting `16:9` widens the 3D camera's aspect by `4/3` and changes nothing else"). The two are different operations that happen to both be called "aspect ratio," and nothing here checks whether they land on the same FOV.

**The authored angle itself is confirmed identical, same day.** `<ExternalCameraFar fov>` was read directly off both discs' own `Data\Ships\<Team>\handlingstats.xml` (`oag-wad cat --expand`, per [handling-stats.md](../docs/formats/handling-stats.md)) for three ships - Assegai, Feisar, Qirex - and all three come back the same value on `pulse-ps2-eu.chd` as on `pulse-psp-eu.chd`. So `AUTHORED_ASPECT` reusing the PSP's *angle* is not an assumption, it is measured: the PS2 disc's design data authors the same base FOV the PSP's does. (Only `fov` was compared; `<ExternalCameraFar>`'s other fields - `lookat_height`/`lookat_length` among them - were not checked and are not assumed to match.)

That narrows, rather than closes, the real question - and it turns out the mechanism side of it is *already* fully documented, in a page this thread had not read closely enough the first time. `docs/ps2/aspect-ratio.md` ("What the option changes: one multiply, in the camera") has the exact function, address and formula, confidence 95: `FUN_0013e280`, at `0x0013e6ec`, multiplies the projection's `aspect` by `4/3` when the `16:9` setting is live, then builds an ordinary perspective matrix from the **unchanged authored FOV** and that widened aspect (`FUN_001e9420`). In its own words: "the option widens the horizontal field of view by a third... at 16:9 the world is not stretched, there is a third more of it across the screen." So this is not unread RE work sitting somewhere else - it is a decided, exhaustively-swept mechanism (every reference to the setting's global is accounted for) that this project's camera simply does not have a counterpart for, on any title.

**A section citing this now exists in `docs/ghidra/functions/ps2-pulse-eu/camera.md`**, so `names.tsv` has a page in the right directory to point at - but `FUN_0013e280` itself is still not named, and turned out not to be the small next step it looked like. Decompiled in full to write that section: the function opens with what reads like a camera-shake/impulse-decay block against a keyed table, pushes a view matrix to the GS display stack, builds the projection (the part that's understood), and afterward computes four-or-more `{xyz, dot}` quads that read like frustum planes. None of that beyond the multiply was analysed. Naming the whole function off the one well-understood address would overclaim what the confidence-95 reading actually covers - the project's own rule is to name what is understood, not the function that happens to contain it.

## Open

- `FUN_0013e280`'s full purpose - the shake/decay block and the plane-like quads noticed while reading it, neither analysed. A name needs that, not just the aspect multiply.
- Whether this project's race camera should reproduce the aspect widen as a selectable in-race setting, separate from `--aspect`'s viewport-shaping role - a design call, not a reading.
- What this does to any pixel-level comparison against a PS2 capture at an uncontrolled `Aspect Ratio` setting: the apparent on-screen size of anything camera-facing (the engine flare's billboard among them) is not comparable between the two builds without knowing which FOV each one actually rendered at.

## Next Steps

- Read the shake/decay block and the plane-like quads in `FUN_0013e280` properly; only then is a whole-function name (and a `names.tsv` row) warranted.
- Decide whether the race camera should widen with a PS2-style aspect option at all, and if so implement it as its own setting rather than folding it into `--aspect`, which already has a documented, different job.
- If a future pixel comparison against a PS2 capture needs the camera geometry to match, pin the PCSX2 profile's `Aspect Ratio` setting to a known value first and compute the matching `--aspect`/FOV on this side rather than assuming either default lines up.
