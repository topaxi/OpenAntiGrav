# HD's `LoadXML` includes are collected and never followed

2026-08-18. `skin.xml` names 21 of them and `oag-game` reads only the root, so the 15 screens it parses are the boot dialogs and `Top FE Screen` - HD's actual `Main Menu` is in `MainMenu_Definition.xml` and is not among them. **The paths need rebasing**, which is the finding: the file spells them `Data\Plugins\PI001\GUI\MainMenu_Definition.xml`, the PSP-style numbered plugin that is *not on this disc at all*, while `Data\Plugins\Frontend\Gui\MainMenu_Definition.xml` resolves (11,035 bytes). The executable composes the skin path from the plugin's own location, so the runtime is presumably rebasing the same way. Following them is not by itself a menu: HD's main menu is a `<HorizMenu>`, and **this build draws one now** without following a single include - the widget's three numbers are in `oag_hd::frontend::MENU_SKIN.strip` per ADR-0022 and `crates/game/tests/hd_menu_ground_truth.rs` reads `MainMenu_Definition.xml` off all five archives that carry it. So **this is still open and is now smaller**: what following the includes would buy is HD's own *screens* and its own menu *tree*, not its layout. Worth doing when the disc's tree is wanted rather than this build's, which `docs/architecture/menus.md` argues it is not.

## Open

- **2026-08-30: resolved by reading HD's real `Skin.xml` off the disc.** `python3 scripts/psarc.py cat data/images/hdfury-ps3-eu-dec.iso:PS3_GAME/USRDIR/DATA00.PSARC /data/plugins/frontend/gui/skin.xml` - the actual file, not a fixture - has 23 `<LoadXML>` elements. **21 of them carry both `Src` and `SrcRel` on the same `<Values>`**, e.g.
  ```xml
  <LoadXML><Values Src="Data\Plugins\PI001\GUI\MainMenu_Definition.xml" SrcRel="MainMenu_Definition.xml"></Values></LoadXML>
  ```
  and the remaining 2 (`Team_Selection_Definition.xml`, `Track_Selection_Definition.xml`) carry `SrcRel` alone, no `Src` at all. There is no rebasing to find because **there are two paths authored side by side, and only one of them needs to resolve**: `SrcRel="MainMenu_Definition.xml"`, joined against the directory `Skin.xml` itself lives in (`/data/plugins/frontend/gui/`), lands exactly on `/data/plugins/frontend/gui/mainmenu_definition.xml` - confirmed present in `DATA00.PSARC`'s own listing, 11,035 bytes, the same file `oag_hd::frontend::names::MAIN_MENU` already reads independently (`crates/hd/src/frontend.rs:146`). `Src="Data\Plugins\PI001\GUI\MainMenu_Definition.xml"` never has to resolve for the disc's own front end to work, because `SrcRel` already does. The `PI001` spelling is exactly the stale-text account reasoned toward earlier today, now confirmed by the disc rather than inferred around it: `Src` is carried-over Pulse-lineage text nobody deleted when `SrcRel` was authored (or the folder was renamed - the two amount to the same thing), not machinery the engine or this build needs to touch. Confidence **92** - a direct, exhaustive read of the real archive file, cross-checked against an independently-recovered resolving path.

That is expected, not a hole in the finding - `hd-frontend.md` already records that the six archives "do not agree on the screen list" - but the other 20 includes' targets were not chased across all seven archives to confirm each one resolves too.
  - Two loose ends, both small: which attribute the original engine prefers when both are present is still unread (this account only needs `SrcRel` to be *tried*, not `Src` to be *ignored* - though skipping straight to `SrcRel` is the only reading that has both authored *and* resolving in the same file); and `crates/game/src/hud/compose.rs::target_of` checks `Src` **before** `SrcRel` for HUD fragments, which is fine there (no shipped HUD fragment carries both - see that file's own header) but would take the dead path first if ever reused as-is for front-end includes, where 21 of 23 do.
  - The earlier vtable-dispatch dead end from this same session (`SVOPluginTagModule::GetPluginTypeAttrib` at `0x7ac6c0`, unreachable through `get_xrefs_to` because this stripped, no-RTTI PPC64 binary has no code-level xrefs into its own vtables) is still worth recording so the next pass doesn't re-spend the hour: it would have named which attribute the engine prefers, and nothing above needed it to close.
- Following the includes would recover HD's own screens and menu tree, not just its layout - not yet done, and now well-scoped: resolve every `<LoadXML>` by `SrcRel` joined against the including file's directory (the same rule `hud/compose.rs::join` already implements), fall back to `Src` only where `SrcRel` is absent, never the reverse. `crates/game/src/screen/tests.rs`'s `SAMPLE` fixture is Pulse's `Skin.xml`, not HD's, per its own header comment - worth a look before reusing it for an HD-side test, since HD's includes carry both attributes where Pulse's evidently do not (unconfirmed either way; not checked this session).
