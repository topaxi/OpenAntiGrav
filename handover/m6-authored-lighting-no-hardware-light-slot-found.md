# M6 authored lighting: no hardware light slot found enabled, and no `DirectionalLight` consumer found anywhere

`AmbientLight`/`DirectionalLight` are registered, `PointLight` genuinely is not, and none of the mesh-draw functions read so far enables a GE light slot. The runtime direction vector recovered along the way is useful evidence for [`lighting.md`](../docs/formats/lighting.md)'s open rotation-versus-translation question. `FUN_08a6b5bc`/`FUN_08a6b5c8` are World/Scene container class stubs, not lighting classes themselves - but `FUN_08a6b5bc` specifically is the class key that identifies the world object, so it is load-bearing for this question, not a dead end (correcting an earlier note on the page). Eight passes total (2026-08-31) ruled out every mechanism this project has been able to identify for reaching the world object: `World_LoadTrack_q` (disassembly-verified pure epilogue after the collection call), `FUN_08886950` (structurally one hop short of the world object), the full class-key enumeration (12 call sites, 10 unique functions, none reads the fields), and `FUN_08930290` (fully characterized as a display-list-baking function, not the "second per-frame draw dispatcher" an earlier pass on this same thread mislabelled it as - retracted in the eighth pass). Full account on [`psp-pulse-eu/lighting.md`](../docs/ghidra/functions/psp-pulse-eu/lighting.md).

## Open

- No GE light slot has been found enabled by any mesh-draw function read so far
- `lighting.md`'s open rotation-versus-translation question for the runtime direction vector is still unresolved
- **`DirectionalLight`'s final consumer is unfound after every mechanism this project could identify has been exhausted.** `World_CollectMarkerLists` genuinely, live-verifiably collects a real per-track `DirectionalLight` list at load - but no reader of it (`world+0x40`/`+0x7c`) exists anywhere the class-key mechanism or `FUN_08930290`'s full characterization can reach. This is not "still searching" - it's a converged negative across everything found so far. Either the collection has a purpose this project hasn't identified, or it has none past track load
- `Mesh_CompileDisplayLists`'s "-1 literal, lighting never baked at compile time" claim is now scoped to that function specifically - `FUN_08930290` bakes the genuine per-material ambient value into its own compiled lists. Doesn't change the M6 conclusion (hardware light slots are disabled inside `Mesh_ApplyMaterialLighting` regardless of caller) but is worth knowing before someone re-derives it
- `World_LoadTrack_q`'s own name is doubtful: it's called from `FUN_08886950` as a generic 60-byte object constructor, not literally handed "the world" - no replacement is anywhere near the 50-confidence floor to act on, so it stays unrenamed and open
- A per-model tint pair (`+0xcc`/`+0xd0`, caller-supplied, consumed by `func_0x0011a464`) surfaced while characterizing `FUN_08930290` - plausibly related to this project's existing per-team-hull-colour work, not chased further here since it's unrelated to `DirectionalLight`
