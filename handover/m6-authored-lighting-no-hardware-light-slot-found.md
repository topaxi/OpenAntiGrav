# M6 authored lighting: no hardware light slot found enabled

`AmbientLight`/`DirectionalLight` are registered, `PointLight` genuinely is not, and none of the mesh-draw functions read so far enables a GE light slot. The runtime direction vector recovered along the way is useful evidence for [`lighting.md`](../docs/formats/lighting.md)'s open rotation-versus-translation question. `FUN_08a6b5bc`/`FUN_08a6b5c8` are World/Scene container class stubs, not lighting classes themselves - but `FUN_08a6b5bc` specifically is the class key that identifies the world object, so it is load-bearing for this question, not a dead end (correcting an earlier note on the page). Passes four and five (2026-08-31) ruled out `World_LoadTrack_q` and `FUN_08886950` for `DirectionalLight`'s missing consumer - the former at the disassembly level (pure epilogue after the collection call), the latter structurally (`Race_CreateModeObject` confirms its `param_1` is one hop short of the world object, and it never reads that hop). A sixth pass enumerated every function that resolves the world object by class (12 call sites, 10 unique functions), decompiled the two remaining ambiguous ones and ruled them out for real (each builds its own fresh, disposable world object rather than looking up an existing one), and closed the `material+0xc4` question `Mesh_ApplyMaterialLighting` raised (write-only across all three of its real callers, one more than this page previously named - the third, `FUN_08930290`, is a second per-frame draw dispatcher the page never mentioned before). Full account on [`psp-pulse-eu/lighting.md`](../docs/ghidra/functions/psp-pulse-eu/lighting.md).
