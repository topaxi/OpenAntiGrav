# The Ghidra DB addresses everything image-base-relative, and it silences every xref tool

2026-08-11, and it cost most of a session. Ghidra renders this program's `lui`/`addiu` constants and `jal` targets as `real_address - 0x08804000`: a string at `0x08a78a2c` reads as `lui 0x27; addiu 0x4a2c`, and a call to `0x0892a050` reads as `jal 0x00126050`. The consequence is that **`get_xrefs_to` and `get_function_callers` return "none" for almost everything**, which reads exactly like "nothing calls this" - it is how the fire path stayed "never found" across three passes. What works is `search_instructions` on the *relative* value, zero-padded (`jal 0x000645cc`). **Re-derived independently 2026-08-19, chasing `Ship_ApplyCollisionImpulse`'s impulse call, before this row was found**: `read_memory` at a `jal` gives bytes decoding to a small sub-`0x08000000` value; the *running emulator's* bytes at the identical address decode correctly, and the two differ by exactly `0x08804000` - the shape of an unapplied `R_MIPS_26` relocation, consistent with this row's own formula. Confirmed on all six `jal`s inside `Body_ResolveContactPair`, including this file's own `0x499f8`/`0x49c60` tail-call row two entries up - both recover their already-believed targets via `+ 0x08804000`, so that finding was right, not lucky. **Not database corruption; no reimport indicated.** Once the fix was known, `search_instructions` on the relative operand found real callers for all three stun functions above in one search each, correcting an overclaim already shipped in this file and in `crates/physics/src/wall.rs`'s doc comment - "reached through a function-pointer dispatch this project has not located" should have read "no static xref, which in this database means nothing until compensated for": `Weapon_PostBlastImpulse_q` is called from `FUN_08867b50` (`0x08867de4`), `FUN_08868ea4` from two sites, `FUN_08868a10` (`0x08868ad4`) and `FUN_088690fc` (`0x08869450`), and `Ship_ApplyCollisionImpulse` from `FUN_0883f540` (`0x0883f5a0`) - none named or read yet, but no longer "unlocated". Full derivation: [contact-response.md](../docs/ghidra/functions/psp-pulse-usa/contact-response.md#its-call-target-needed-the-image-base-added-by-hand---ghidras-own-bytes-are-pre-relocation). **Also stale**: `apply-ghidra-names.py` no longer fails 133 of 151 rows - re-measured 2026-08-19 at 515 applied, 1 failed (`0x0885eb54 ShipShield_InitColours`, unrelated), so whatever this row's number was measuring has since been fixed; the mechanism note above stays right, the count did not.
