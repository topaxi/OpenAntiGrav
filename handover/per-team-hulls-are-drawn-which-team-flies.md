# Per-team hulls are drawn; which team flies which slot is not recovered, and the paints are not read

2026-08-15, `crates/game/src/livery.rs`. Every grid slot loads its own team's `Ship.vex`, `shipboost.vex`, `Engine Flare` locator and `Ship Collision Fx` anchors; `race::load` returns `Vec<Livery>` and `Scene` builds a `Drawable` per slot from it. **Measured first, because it decided the test**: the eight teams the PSP disc declares are eight *different models* - 845 to 1,497 triangles, radius 6.45 to 7.09 - where every team's *Zone* hull is byte-identical geometry and differs only in paint. So the ground-truth test counts distinct triangle counts, which would be vacuous on Zone. **Two things are open.** (1) **The slot assignment is this project's.** `Race_SpawnAiRacer` takes an `id` from a racer list built upstream that nothing has read, so the original may draw teams by championship entry, by player choice or at random; `livery::teams_for_slots` fills from the catalogue in file order and the load report says so on every run. (2) **`PI_TeamModel`/`PI_ModelSkin` are still unread**, and they are *not* what this row closed - they are the alternate paints with `loyalty` unlock thresholds, and `PI_TeamModel`'s `location` is a **file stem** (the literal `"ship"`), which is the `shipwreck.vex`-not-`Assegaiwreck.vex` trap. **The list length cuts both ways**: with all four DLC packs mounted the catalogue is twelve teams for eight slots and the extras do not race, while Pure and the PS2 set can be *shorter* than the grid, where the list cycles and the report names the repeat. Sparks still use slot 0's anchors alone, because `oag_render::sparks` triggers off the player's contacts only.

## Open

- **Live capture found Custom Race / Single Race - the mode this project implements - never reaches `Race_SpawnGrid`/`Race_SpawnAiRacer` at all**, and its real spawn path (`FUN_0882e57c`/`FUN_088285e0`, `docs/ghidra/functions/psp-pulse-usa/grid.md#custom-race-does-not-go-through-race_spawngrid-at-all-and-hardcodes-id-to-0`) hardcodes the `id` field to `0` for every racer. So `Race_SpawnGrid`'s `id`/team-catalogue mechanism (confidence 90 on its own mechanics, see grid.md's other new section) does not answer "which team flies which slot" for the mode that matters - it's either Career/Championship-only (untested this session) or unused entirely.
- **`Craft_Construct_q` is ruled out as where Custom Race picks a team.** Read in full this session (`0x08840c74`): it initialises physics/hover/shield/particle state off `param_2` (a small 0-3 role tag, not `id` or a team index) and never references `DAT_00057c44` or any `.vex`/team-path string. `search_strings` for `Data.Ships`/`Ship.vex` across the whole binary found nothing either - the path is very likely built at runtime from a team-name substring plus a fixed suffix, not present as one literal. So team assignment for Custom Race happens somewhere neither spawn chain nor its shared constructor touches - unfound this session
- `PI_TeamModel`/`PI_ModelSkin` (alternate paints with `loyalty` unlock thresholds) are still unread
- With all four DLC packs mounted, the catalogue is twelve teams for eight slots and the extras do not race
- Sparks use slot 0's (the player's) anchors alone, not the full grid

## Next Steps

- `Craft_Construct_q` is read and ruled out (above) - do not re-read it looking for team assignment. The next lead is the **renderer/asset-loading side rather than the entity constructors**: something reads a per-slot team name and builds a `Data\Ships\<Team>\` path from it, probably close to where the model actually loads rather than where the physics entity is constructed. A live memory *write* watchpoint on wherever this project's own `race::load` first reads a team-select result would settle it fastest, but this PPSSPP debugger's breakpoints are execution-only (`cpu.breakpoint.add`) - no write-watch support was tried or found this session, so this may need `find_undocumented_by_string`/`list_strings` swept for a narrower filename fragment (a team's own name, e.g. `Assegai`) rather than the generic `Ship.vex`/`Data.Ships` patterns that came up empty, or a slower single-step trace forward from `FUN_0882e57c` itself.
- Breakpoint methodology that worked this session, for whichever function is tried next (`scripts/psp-drive.py` + `ppsspp_debugger.Debugger`): arm a breakpoint on the entry, drive `psp-drive.py menu --single-race` in a **separate** process/call so the CPU keeps running while the breakpoint stays armed, read `cpu.getAllRegs()` on the hit. **Do not trust a static "+ image base" address guess for a live read** - `&DAT_000577f8 + 0x08804000` (`0x0885B7F8`) was tried this session and landed on live MIPS *code* bytes, not the struct; reading the base straight out of a live register at a breakpoint (`a0` at `FUN_08806bbc`'s or `FUN_0882e57c`'s own entry) is what actually worked and should be trusted over the naive transform.
