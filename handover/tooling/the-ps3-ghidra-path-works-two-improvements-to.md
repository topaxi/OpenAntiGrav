# The PS3 Ghidra path works; the cspec-only fork is done, `lvlx` is what's left

2026-08-17. Importing `EBOOT.elf` needs no processor module - stock Ghidra decodes the Cell PPU as `PowerPC:BE:64:A2ALT-32addr` - but it does need a decrypt step, a hand-edited compiler spec and a script pack. Full procedure and its traps in [toolchain.md](../../docs/reverse-engineering/toolchain.md#ps3). *(3) A headless import script* - `scripts/import-ps3-eboot.sh` drives `analyzeHeadless` with the loader, the processor and the pre/post scripts in one command, decrypts the SELF first if the ELF is missing, and refuses to run without the cspec fix or while Ghidra holds the project lock. `scripts/apply-ghidra-names.py`'s `BINARY_PROGRAMS` also has its `ps3-hdfury-eu` row now.

**2026-08-26: (1) done.** The cspec-only fork does not need vendoring at all, confirmed by reading `SleighLanguageProvider.java` (Ghidra's own source, shipped as `SoftwareModeling-src.zip`): a `.ldefs`'s `slafile`/`processorspec`/`compiler spec` attributes each resolve first beside the `.ldefs` itself, then fall back to an application-wide search by filename across every installed module - so an extension can point at stock Ghidra's own `ppc_64_isa_altivec_be.sla` and `ppc_64.pspec` by name without vendoring either, as long as the filename is unique across the install (checked: it is). `scripts/ghidra-ps3-language/{ppc_64_32_ps3.cspec,ppc_ps3.ldefs}` define a second language, `PowerPC:BE:64:A2ALT-32addr-PS3` (a new id was unavoidable - Ghidra rejects a duplicate rather than letting one override the other), whose cspec is the currently-patched `ppc_64_32.cspec` verbatim. `just build-ps3-scripts` (`scripts/build-ghidra-ps3-scripts.sh`) copies both into the Ps3GhidraScripts checkout before building, so the built extension always carries the fix alongside the scripts. Verified: built, installed into `~/.config/ghidra/*/Extensions/Ps3GhidraScripts` (with a `.oag-backup` of the prior install), and imported via `analyzeHeadless` against a scratch project - `Using Language/Compiler: PowerPC:BE:64:A2ALT-32addr-PS3:default`, import succeeded - all done against a separate throwaway project so the live `OpenAntiGrav.gpr` (open in Ghidra throughout, 26,100 functions) was never touched.

**Was deliberately not wired as the default; now is.** `scripts/import-ps3-eboot.sh --ps3-cspec` opts in; the plain invocation still imports under the stock id with the root-owned patch, unchanged. Switching the live project over meant a fresh reimport under the new id - Ghidra does not migrate a program between language ids - which is safe by this project's own rule (`just apply-names` reproduces the recovered names onto a fresh import) but was slow enough on 26,100 functions that it stayed a deliberate maintainer choice rather than a side effect of this thread. **Done 2026-08-28** (see `HANDOVER.md`'s "Traps that are live" for the full verification writeup): the maintainer ran the `--ps3-cspec` reimport, `AssignPs3R2FromOpd.java` now runs as part of the normal import script, and `live open_programs` confirms it as of 2026-09-03 - `ps3-hdfury-eu`'s `EBOOT.elf` reads `PowerPC:BE:64:A2ALT-32addr-PS3`, still 26,100 functions. Whether to also open a PR to upstream clienthax/Ps3GhidraScripts is separately undecided and not done here - same "ask first" rule this thread already applied to `lvlx`.

## Open

- Sleigh does not decode `lvlx` (851 sites in `EBOOT.elf`), which is what would force vendoring the 21 `.sinc` files if teaching it is attempted the way the cspec-only fork's `@include` constraint originally implied it would (the cspec-only path itself needed none, since it never touches sleigh - see above).
- Whether to publish `scripts/ghidra-ps3-language/` upstream is a maintainer decision - not made here.

**Closed 2026-09-03: no `.opinion` file is possible for this language, and that's a real answer, not a gap.** Traced Ghidra's own loader (`ghidra/app/util/opinion/ElfLoader.java`, from `Base-src.zip`): `findSupportedLoadSpecs` queries `QueryOpinionService.query(name, machine, ...)` on exactly two ELF-derived keys - `elf.getMachineName()` (the `primary=` constraint, `"21"` for `PowerPC64`) and `elf.getFlags()` (a `secondary=` bit pattern, i.e. `e_flags`). **`EI_OSABI` (`e_ident[7]`) is never consulted by the ELF loader's opinion matching at all**, regardless of value. It *is* a real, standard, PS3-specific value here - `0x66` (102 decimal, confirmed via a raw hex dump of the file, not just `readelf`'s `<unknown: 66>` label) is `ELFOSABI_CELLOSLV2`, documented in the PS3 homebrew toolchain ecosystem (psl1ght, PS3 SDK headers) as CellOS Lv-2's own OS/ABI marker, and no generic PPC64 Linux ELF uses it - but Ghidra's ELF `.opinion` grammar has no hook to key on it. The other candidate, `e_flags`, is `0x0` on `EBOOT.elf` (confirmed via `readelf -h`), which is generic and not PS3-specific either. So: the language still has to be chosen by hand at import time, permanently, short of a custom Ghidra loader extension (out of scope here) - not a gap to revisit.
