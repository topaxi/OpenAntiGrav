# A global reached through `$gp` has an instruction displacement unrelated to its address

2026-08-17, found while looking for what writes `DAT_08b32428`. Program-wide there is **no** instruction whose operand text contains `0x2428`, yet the decompiler shows reads and writes of that global all over the weapon code. The PSP ELF uses `$gp` for small data, so the access is `lw v0, <small gp offset>($gp)` and the address never appears as an immediate anywhere. **Consequence, and it is the third trap of this shape in two days**: a displacement sweep on a global's low half can return zero hits on a global that is read constantly, and that zero looks exactly like "nothing touches it". It does *not* undermine the `WeaponAIstats` sweeps - that record is heap, reached through a `this` pointer, not `$gp` - but any future "nothing reads this global" claim has to rule `$gp` out first.

**2026-09-05: the `$gp` diagnosis above was wrong, and the writer is now found statically.** Checked directly: `search_instructions` for the substring `(gp)` (any mnemonic) across this program's entire 521,965 instructions returns **zero** matches, and `SceModuleInfo.gp_value` (`.rodata.sceModuleInfo`, struct offset `0x20`) reads `0`. This binary's compiler never uses `$gp`-relative small-data addressing at all - `$gp` is not the mechanism here or apparently anywhere in this program. The real mechanism is the *other* already-documented trap: a naive/pre-relocation `lui`/`addiu` HI16/LO16 pair that Ghidra's relocator never fixed up, so the decompiler shows a small, wrong-looking constant instead of the real address, and neither `$gp` nor the real address's low bits appear anywhere in the instruction stream - which produces the exact same "zero hits" symptom this thread describes, just via a different addressing mode than guessed. The general lesson stands and is now sharper: **before concluding a global is `$gp`-relative, first check for zero `(gp)` operands program-wide** - if there are none, the binary doesn't use `$gp` addressing at all, and the fix is the naive-value/relocation-base trap instead.

`DAT_08b32428` (the WeaponStats file selector: `0` in Single Race, `1` in Eliminator, per [missile.md](../docs/ghidra/functions/psp-pulse-usa/missile.md)) is written in exactly two places, both per-race-mode constructor case blocks reached from `Race_CreateModeObject`'s (`0x08821038`) mode-dispatch jump table - a compiler-generated `switch` that Ghidra's decompiler failed to resolve (it emits the literal warning `Could not emulate address calculation... Treating indirect jump as call`, and none of the 18 case blocks have a `Function` defined at them; they had to be read with `disassemble_bytes(dry_run=true)` on raw, unanalyzed bytes):

- **Single Race (mode 3), `FUN_0882bfd4`, `0x0882c2e8`:** `lui a1,0x6 ; addiu a1,a1,-0x7030 ; sw zero,0x8(a1)` (the `sw` is the branch's delay slot, so it always executes) - writes `DAT_08b32428 = 0`.
- **Eliminator (mode 8), `FUN_0882c880`, `0x0882cb38`:** `lui a2,0x6 ; li a1,0x1 ; addiu a2,a2,-0x7030 ; sw a1,0x8(a2)` - writes `DAT_08b32428 = 1`.

Both match missile.md's independently live-measured values exactly. Confidence **88**. Full derivation, including a validated naive-address correction constant (`+0x08ad9450`) that **conflicts with and refines** [anim-transform.md](../docs/ghidra/functions/psp-pulse-usa/anim-transform.md)'s "second relocation base... there is no third base to find" claim (see that page for the correction), is in this session's evidence trail; see [missile.md](../docs/ghidra/functions/psp-pulse-usa/missile.md) for the write-site citation now added there.

## Open

- Whether `FUN_0882bfd4`/`FUN_0882c880` deserve full names (e.g. `RaceMode_ConstructSingleRace`/`RaceMode_ConstructEliminator`) is open - only the one field documented above was verified; the rest of each function (RTTI registration, a per-craft init loop, several flag-word `ori`s) was not read closely enough to name the whole function with confidence.
- The naive-value relocation-base correction is per-relocation-entry, not per-segment as previously believed (see the anim-transform.md correction). No general rule for computing it without an instruction-level cross-check was found; `run_script_inline`/`run_ghidra_script` (which could read the raw `.rel.text` records directly, as anim-transform.md's own confirmation did) are gated by `GHIDRA_MCP_ALLOW_SCRIPTS` and were not enabled (shared Ghidra bridge).
