# HD's strip widget draws bare text; the real menu also draws a tab shape, an underline, and a background scene

2026-09-01. Grew out of a now-closed thread on HD's horizontal main menu, whose two open questions (the `selected` colour and whether the strip carousels) this closed with a live RPCS3 capture (`scripts/rpcs3-drive.py`, boot chain to `Main Menu`, then `Additional` -> `settings`/`Game Options`; screenshots under `data/reference/hd-main-menu-screenshot*`, `hd-menu-highlight-shift`, `hd-menu-style-toggle*`, `hd-settings-screenshot*` on the machine that captured them - gitignored, not committed, reproduce with the commands in the doc citations below). Full evidence and confidence scores are on [hd-frontend.md](../docs/formats/hd-frontend.md#the-fe-style-switch-is-live-works-and-is-not-an-archive-swap---confirmed-by-capture); this is the implementation side of the same finding. Three gaps, all in `crates/game/src/menu/strip.rs` and `crates/game/src/menu/frame.rs`, neither of which draws anything beyond text and the flat frame chrome today:

1. **A `<HorizMenu>` entry has a background tab, and `strip::draw` draws none.** The real widget is a right-slanted parallelogram, filled `HD_Grey` when unselected and `HD_Blue` when selected (`0xffac0717` red on the served Fury style, `0xff8ac0ca` teal on HD), with a short underline mark under the selected label alone. None of that shape is authored in the `<HorizMenu>` XML itself - only a position and one literal colour (`0xff705070`, unidentified - it matches neither the fill nor the text in either style) - so it is native engine chrome, not a texture or a declared widget this project can point `oag-formats` at. `strip::suits`'s four screens (`Main Menu`, `Additional`, `Extras`, `Controls Menu`) all draw this way.
2. **`Skin::selected()` brightens the text; the real game does not.** The capture shows the selected and unselected entries in the *same* white `TextColor`, at the same weight, in both styles - what changes is the tab fill and the underline, both gap 1. So `selected()` should read the same as `normal()` unconditionally, and the highlight moves entirely onto the new tab-shape mechanism once it exists. Shipping gap 2 alone (dropping the current white-on-selection) without gap 1 would make the selected entry *less* visible than today, so land them together.
3. **HD's `Top FE Screen` carries a `<BackgroundAnim>` and this build draws nothing there at all.** `docs/formats/hd-frontend.md` already named `FrontEndScene_HD_ATG.vex`/`.rcsmodel` at confidence 88; the capture adds that *something* real-time and animated (dense red/gold particle motion, no fixed image, different between two boots) draws on the served Fury style, and nothing draws on the HD style - flat white, no motion. `renderer.md`'s shader census names `FEBackgroundAnimFuryWave`/`FEBackgroundAnimFuryBlend` among nine `FEBackgroundAnim*` programs, which is the more precise hypothesis this capture supports: a style-specific *shader* over shared or per-style geometry, not one mesh drawn the same way regardless of style. `.vex`/`.rcsmodel` decoding is its own open item - `hd-status.md` already reads `.vex` byte-swapped but the mesh batches moved to `.rcsmodel`, and neither this thread nor the capture settles that.

**What this is not**: none of the three is a rendering bug in an existing feature - they are unauthored chrome this project has never attempted, so there is no regression to chase, only work to scope. Per `CLAUDE.md`'s rule against inventing a stand-in, gap 3 in particular should stay undrawn rather than get a plausible-looking placeholder scene until the real geometry/shader is decoded or at minimum located.

**One thing this capture also exposed, worth remembering before `<aImage>` ever gets a parser**: `DATA00`'s own `mainmenu_definition.xml` opens with the comment `<?this is the real menu ?>` and carries an `<aImage>` block named "Temporary Colour Check" - four swatches naming `HD_Blue`/`HD_Grey`/`HD_LightGrey`/`HD_White`/`HD_BG` by their live value, clearly a developer debug overlay. `<aImage>` is not a tag anything here recognises today, so it is inert by omission rather than by a considered exclusion - but the retail capture also shows no trace of it on either style, confirming the omission happens to be correct. When `<aImage>` (or any other still-unhandled tag) does get read, this specific instance needs the same treatment `frame.rs` already gives `FE_TRIAL_MODE`/`FE_PURCHASE_NOW`: excluded on purpose, not drawn because it parses.

## Open

- Whether gap 1's tab shape is a fixed-function primitive (a coloured quad with a skew) or comes from an undecoded texture/font-adjacent asset - no candidate texture name was found in a `Data/FE/Images` sweep of `DATA00`.
- What the `<HorizMenu>`'s own literal `color="0xff705070"` is for - it matches neither the tab fill nor the entry text in either style.
- Whether HD's style genuinely draws nothing behind the menu or draws something too subtle/slow to show in one capture (`ScreenSetting name="Main Menu" blur="0"` at least says the screen is meant to be sharp).
- Which of the seven non-Fury `FEBackgroundAnim*` shader names (if any) the HD style resolves to.
- `.vex`/`.rcsmodel` decoding generally - a prerequisite for gap 3 regardless of the shader question.

## Next Steps

- Fix `Skin::selected()` to return the same value as `Skin::normal()` (gap 2), landed together with the first cut of gap 1 so the selection indicator does not regress in between.
- Design and implement the tab background shape for `strip::draw` (gap 1): read the parallelogram's exact geometry off a capture (angle, padding around the label, corner treatment) since nothing on disc states it.
- `.rcsmodel`/`.vex` decoding is already tracked elsewhere (`.rcsmodel` appears across several open threads, e.g. [a-chunk-header-is-0x20-bytes-and-then.md](a-chunk-header-is-0x20-bytes-and-then.md)); gap 3 is blocked on that work landing, not on starting it fresh.
