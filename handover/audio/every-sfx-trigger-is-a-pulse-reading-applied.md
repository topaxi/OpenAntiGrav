# Every SFX trigger is a Pulse reading, applied to Pure and HD on a bet

Split out 2026-09-02 from `hds-bnk-sound-banks-read-and-hd-makes.md`, whose own scope (the `.bnk` container format and both waveform codecs) is now fully resolved and closed. This caveat was carried in that thread's opening paragraph but was never actually part of its `## Next Steps`, and it is not really about bank *decoding* at all - it is about the nine [`oag_sound::sfx::Cue`](../../crates/sound/src/sfx.rs) variants, each of whose trigger (`SpeedupPad`, `Collision`, `Absorb`, `Engine`, `Shield`, `ShieldActive`, `Disengaging`, `Blowup`, `LockOn`) was recovered from **Wipeout Pulse's PSP executable only**. `crates/sound/src/sfx.rs`'s own module doc already states this plainly: *"no Pure or HD dispatch has ever been looked at. Firing a Pulse-recovered edge on those titles is a bet ... Reasonable, and not a reading; confidence 50."* That confidence-50 line is the reason this is worth its own thread: it is below this project's naming and trust threshold on two of the three titles this engine plays, for every single wired sound effect.

## Open

- Whether Pure's executable calls the same `Sound_Play`/`Sound_PlayLooping` sites at the same simulation edges Pulse does, for the remaining **one** cue, `Blowup` - all eight others are now confirmed (2026-09-04, see `docs/ghidra/functions/psp-pure-usa/rocket-and-collision-fx.md`, `shield-sound.md`, `dry-play-cues.md`, `exhaust-sound.md` and `lockon-sound.md`). `Blowup`'s Pure call site is a **genuine blocker**, not just unstarted - see `blowup-sound-open.md` for six exhausted search methods and why the next step needs a different strategy, not another arithmetic guess.
- Whether Wipeout HD's PS3 executable does the same, for all nine cues. HD's `ShipCollisionFx_Trigger`, `Exhaust_UpdateEngineSound`, `Shield_Activate` and so on are presumably different functions at different addresses in a different binary (PPC64, per-function TOC defect - see `docs/ghidra/functions/ps3-hdfury-eu/memory.md`), not yet located.
- Whether the *gating* logic matches, not just the call site's existence - confirmed for `Collision` and `Absorb` on Pure (same cooldown/stagger shape, one real difference found: `Absorb`'s stagger loop runs 8 times on Pure against Pulse's 10); confirmed for `Shield`/`ShieldActive`'s **call order and cue names**, but Pure's `shieldactive` call reads unconditional where Pulse's is gated on a field `shield-sound.md` didn't chase; confirmed the same shared dry-play chain (now identified end to end, `Scream_PlaySoundByName` on both sides) fires `SpeedupPad` and `Disengaging`, but `Disengaging`'s own countdown threshold on Pure is unread (`dry-play-cues.md`); `Engine`'s voice-open edge confirmed with two exactly-matching tuning constants (`-1143.0`, `0.01`), but its per-tick pitch/volume write is unchecked (`exhaust-sound.md`); `LockOn` confirmed near line-for-line, including the shared choice to bypass the gate helper (`lockon-sound.md`). Still fully open for `Blowup` and for HD entirely.
- **Pulse's own `Blowup` trigger is now read precisely for the first time** (`blowup-sound-open.md`): `Ship_SetState`'s case 4 sits at an address with no Ghidra function boundary, reached only through a 9-entry indirect jump table, and its `~BLOWUP` call is an *indirect* string load (a pointer-table slot, not a direct build) - unlike most of what this thread found on Pure. That the shape differs from Pure's usual direct-build pattern for other cues is itself a clue, not yet used: Pure's `Blowup` string may also sit behind an indirect load this session's direct-build searches would not catch, in a pointer shape distinct from the one byte-pattern search already tried.

## Next Steps

- **`Blowup` needs a different search strategy, not a retry of what's already documented as exhausted in `blowup-sound-open.md`.** Three real options: (1) find Pure's own `Ship_SetState` counterpart by walking from something it's known to touch - `Ship_ApplyPendingWeaponDamage`, `Ship_DispatchCollisionFx` or another already-named Pulse function this cluster calls, cross-referenced the same way `ShipCollisionFx_Trigger`'s own callers were sought, rather than fuzzy-matching `Ship_SetState` itself (already tried, false-positive shape). (2) Accept the indirect-load hint above and search Pure systematically for pointer-table slots holding `0x08a7a648`'s address in *some* transformed form, not just the one raw byte-reversed pattern already tried - e.g. the table might sit at a different base than assumed, or hold an offset rather than a full address. (3) **Search for `jalr` (register-indirect) calls into the dry-play chain's gate/middle hop, not just literal `jal` targets** - this session's two caller sweeps (`blowup-sound-open.md` methods 4-5) only find static `jal` callers, and the one confirmed fact about how both binaries reach a `Blowup`-shaped handler is that it's itself only reached through an indirect jump table, which makes a register-indirect call into the chain plausible and unchecked.
- All eight confirmed cues' corroboration is decompilation-only (confidence 78-82, capped by the `85`+ band needing a runtime trace); a PPSSPP capture of any of the Pure trigger functions named across `rocket-and-collision-fx.md`, `shield-sound.md`, `dry-play-cues.md`, `exhaust-sound.md` and `lockon-sound.md`, the way `docs/reverse-engineering/ppsspp-debugger.md` already does for Pulse, would raise them past that ceiling if anyone picks this thread up for verification instead of coverage.
- `oag-wad sounds <archive>` lists the cues each bank actually carries per title, useful for confirming a candidate cue name exists on Pure/HD before spending time hunting its trigger - this is how all eight confirmed cues' names were checked present in Pure's banks before the Ghidra read, and how `~BLOWUP`'s presence on Pure's disc was confirmed even though its trigger wasn't.
- **`search_strings` on a candidate address first, arithmetic and `jal`-wart search second - and `search_byte_patterns` when `search_strings` comes up empty.** Every cue found this session started from `search_strings` locating the literal cue name directly in Ghidra's own string index; `~BLOWUP` needed the raw-byte fallback because Ghidra never auto-detected it as a string data item (the same gap `TURBO` showed in `dry-play-cues.md`) - that fallback found the string's address cleanly, just not its caller.
- **Before writing "X is a flat/simple/one-hop Y", grep `sfx.rs` and every doc page that already cites the function.** A same-session pass wrote that claim about Pulse's dry-play helper without checking what it actually calls, and had to correct it once `Disengaging`'s own citation (`FUN_0883e9b0` -> `FUN_0893a768`) was reread - a claim already on record beats a fresh read of one call site. Separately, a spawn-helper address was first computed wrong (`0x0886de1c` instead of `0x08871e1c`, a `0x4000` slip), caught only by decompiling the candidate and comparing it structurally against the Pulse function it claimed to match - "is a function entry" alone did not catch it.
- **This is the thread's natural stopping point for this session** - eight of nine cues confirmed on Pure with a genuine blocker on the ninth, not an unstarted one. HD (a different binary, a different toolchain trap, the `0x32d5e0` TOC break) is a separate front and should be its own session's work, per this thread's own standing advice, rather than started cold right after a blocker.
- HD's PPC64/TOC binary is still the harder half and can follow once more of the PSP-side pattern (Pure vs Pulse) is established, or be picked up independently.
