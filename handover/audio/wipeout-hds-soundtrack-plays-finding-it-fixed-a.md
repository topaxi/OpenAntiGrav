# Wipeout HD's soundtrack plays; finding it fixed a disc-wide PSARC bug

2026-08-17. 36 plain MPEG-1 Layer III files under `/data/music/`, read through the same `oag_raceplay::catalogue::music` schema all three titles share. **The bug, not specific to music**: `oag_formats::psarc` applied the `0x78` zlib-marker test to every block including full-size stored ones, which are raw by definition - one MP3 block that happens to start `78` was handed to `miniz_oxide` and the whole entry read as unreadable. Fixed and pinned by a fixture; any HD asset with such a block was affected. `symphonia` (MP3 only, `default-features = false`) is now the dependency for this path rather than ffmpeg, per [ADR-0024](../../docs/architecture/adr/0024-in-process-codecs-and-ffmpeg-as-a-last-resort.md). `crates/game/tests/hd_music_ground_truth.rs` (9 tests), [hd-status.md](../../docs/formats/hd-status.md#music-plain-mp3-declared-the-way-the-psp-titles-declare-theirs). The `CustomMusicManager`/`/dev_hdd0/` strings in the ELF are the PS3's own custom-soundtrack feature, not disc content - not a thread.

**2026-09-08: the first Open item below was stale, not open.** It was written the same day `oag_hd::TITLE.front_end` went from `None` to `Some` (a few hours later, per ADR-0025), and nobody had re-checked it since. A headless `just play hd --dump-audio` run logs `audio: music Data\Music\FEMusic\frontend1_stereo.mp3, 170.7 s, looping` - the front-end music does play in a real boot, ours at least; `hd-status.md` and `hd_music_ground_truth.rs`'s doc comment are corrected. HD's front-end boot chain is also `Provenance::Measured` since 2026-09-05 (three RPCS3 cold boots, ADR-0025/hd-frontend.md), which several other stale references (`justfile`'s `play` recipe comment) called out as still-declared - fixed alongside.

## Open

- **Which of the four front-end cuts the *original* plays is still unread.** The 2026-09-05 RPCS3 capture watched the screen order, not the audio, so it settled nothing here; `oag_hd::names::FRONT_END_MUSIC` picking base stereo is our own choice; matching the original needs an RPCS3 audio capture (or an `RPCS3.log` `cellFsOpen`/`sys_fs` trace naming the file it actually opens) that nobody has run yet.
- `FEship.mp3`'s builder is now located - `Music_BuildFeshipTrackPath` (`0x0017acc0`, confidence 78, [sound.md](../../docs/ghidra/functions/ps3-hdfury-eu/sound.md#music_buildfeshiptrackpath-the-front-ends-second-track)) copies either `FEship.mp3` or `FEship_surround.mp3` and forwards it to an open-then-play helper - but **no call site exists anywhere in the binary**: it is reached only through an indirect dispatch this session did not find. `search_instructions(mnemonic=bl, operand_pattern=17acc0)` and a search for its own `.opd` address as an immediate both come back empty. **2026-09-15: re-confirmed on the post-`lvlx` image**, this time also by a whole-image literal-address scan for the function's `.opd` descriptor and its raw code address (`toolchain.md#ps3`'s validated method, not just the two searches above) - neither address appears anywhere in the binary except the function's own `.opd` entry. See [sound.md](../../docs/ghidra/functions/ps3-hdfury-eu/sound.md#music_buildfeshiptrackpath-the-front-ends-second-track) for the full method and self-check. Still no caller found; either it is genuinely dead code in the shipped build, or it is reached through machinery (a computed pointer, not a stored one) this project's static tools cannot see.
- Base-stereo versus `_fury` front-end music cuts are confirmed different encodes (a 4x size gap, not two encodes of one), but which plays when is unwired in both our engine and the original.
