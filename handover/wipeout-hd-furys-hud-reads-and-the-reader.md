# Wipeout HD / Fury's HUD reads, and the reader it shares with Pulse was wrong in three ways Pulse's own data could never have shown

2026-08-17. All **eighteen** of HD's shipped HUD layouts compose with **nothing missing and nothing skipped**, into 2,320 widgets - cross-checked against a second walker written in the test file, because Pulse's `grep`-the-file trick does not survive a layout that is 17 files. `oag_hd::hud`, `oag_game::hud::compose`, `crates/game/tests/hd_hud_ground_truth.rs`, [hd-hud.md](../docs/formats/hd-hud.md). **HD's HUD is Pulse's HUD composed out of fragments**: a mode's root is a shell of 1-2 KiB that pulls in up to sixteen more by `<LoadXML SrcRel=... DirectEmbed="true">`, 720 of 720 includes on the disc spelled that way and none with `Src`. **Three rules, each of which Pulse's own five layouts are silent about.** (1) **`SrcRel` resolves against the including file's directory**, which is the only thing making the three skins distinct - `/data/xml/elimination_hud.xml` and `/data/xml/wo3_hud/elimination_hud.xml` both name `HUD_elim_line.xml` and mean different files - and **`..` ships**: Duel reaches four fragments as `..\HUD_colours.xml`, so a reader that concatenates loses a quarter of that mode's HUD with an error that reads like a missing file (5 files -> 9 once the segment is applied). (2) **`OffsetX`/`OffsetY` compose down the tree and `x`/`y` do not.** The walker read an `<Item>`'s offset as *absolute* on the stated grounds that "nothing in the shipped data nests them" - true of Pulse (26 offsets, all `<Item>`, 0 nested) and false of HD (218 offsets, 116 of them on widgets, 242 widgets holding widgets). (3) **A nameless widget is drawn, not broken.** Both widget readers required a `name` and recorded the loss in `skipped`; Pulse names all of its, HD leaves **106** anonymous against 2,214 named, mostly `BackgroundLayer="1"` panels behind a named readout. **And the layouts name source art rather than shipped files**: `hdHUD.mip` (148 sprites) and `detonator_hud2.tga` (44) are the two most-used references and neither extension exists on the disc - both resolve with the extension replaced by `.gtf`, so 12 of 12 references land instead of 10. `oag_hd::hud::texture_entry`, confidence 85, **no executable path read for it**. **One thing to know before continuing.** `docs/formats/hd-hud.md`'s counts are the composition *this build* performs: six of the eighteen roots ship in **more than one archive at different sizes** (`elimination_hud.xml` is 1,856 bytes in `DATA00` and 5,666 in `DATA02`), `oag_assets::Archives` picks by this project's own precedence, and **whether the original picks the same copy is unread** - the test pins it per root so a change to the archive order shows up there rather than in a screenshot. Both of this row's holds - no `.gtf` decoder, no pixel drawn - are discharged.

## Next Steps

2026-08-25, first pass: spent ~45 min in `/ps3-hdfury-eu/EBOOT.elf` chasing the extension-rewrite question by string search, confirmed a negative rather than a mechanism, and stopped rather than guess. What was checked:

- `search_byte_patterns` for the raw bytes `2E 67 74 66` (`.gtf`) - every hit falls inside a full path string Ghidra had already defined (e.g. `Data\FE\Images\badges.gtf`). No hidden, un-defined `.gtf` literal exists anywhere else in the binary.
- A regex bare-context search (`[^.]gtf`, i.e. a `gtf` not preceded by a dot) turned up exactly one hit beyond the leading-dot path strings: `image/gtf` at `007a7e18`. Traced its one caller (`FUN_00328f70`, a trivial getter) up to its only caller (`FUN_002b86a0`), which is a large state machine referencing `"AdServer Not Found"` and driving `cellFsOpen`/`cellFsLseek`/`cellFsClose` - **PS3's downloadable-ad-content cache, not the HUD texture loader.** Dead end. **Verified, not just decompiled**: both functions' real TOC (`scripts/ps3-toc.py toc`) is the global `0x008ad4d8`, so Ghidra's decompile of them is trustworthy - see the TOC-trap paragraph this session added to `HANDOVER.md`'s Traps section before trusting this.
- Confirmed the two literal source-art names (`hdHUD`, `detonator_hud2`) are absent from the executable's own string table entirely (`search_strings` on both, zero hits) - they only exist in the disc's XML.

2026-08-25, second pass (Ghidra sweep proper, following dataflow rather than strings): this is where the session's real finding turned up, and it's a methodology trap, not the rewrite mechanism.

- `get_xrefs_to` on the `SrcRel` literal (`0078bf28`) reported a hit inside `FUN_00550eb4`, which decompiles as exactly what this thread was hunting: a `LoadXML_Item.cpp`-attributed function checking `strncmp(param_2, "Values", 0xb)`. **It is a false lead.** `scripts/ps3-toc.py toc 0x00550eb4` gives `0x008bd3c4`, not the global `0x008ad4d8` Ghidra assumed - the function is actually `CCookie.cpp`'s `Set-Cookie:` header parser (the `0xb` is `"Set-Cookie:"`'s 11 characters, not `"Values"`'s 6; confirmed directly by reading its real TOC's neighbouring strings - `Set-Cookie:`, `expires`, `domain`, `path`, `secure`). Full account in `HANDOVER.md`'s Traps section - **any `get_xrefs_to` result or decompiled symbol name for a TOC-relative load needs `scripts/ps3-toc.py toc <addr>` checked before it's trusted**, binary-wide.
- Found the *real* `LoadXML_Item.cpp` via `scripts/ps3-toc.py attrib 0x0078bf00` (the `__FILE__`-attribution trick, which doesn't go through Ghidra's TOC-corrupted xrefs at all): three functions, `0x001c1f30`/`0x001c2988` (constructors) and `0x0069bcf0` (allocator). Reading the class's own attribute-name table directly with `inspect_memory_content` at `008ad9f0` (raw pointer array, no TOC involved) gives the real list: `Values`, `Src`, `SrcRel`, `localised`, `PlatformSpecific`, `CheckForSD`, `Debug`, `DirectEmbed`, `%s\%s`, `true`, `1`. **This confirms `LoadXML_Item` is the `<LoadXML>` fragment-include mechanism** (matches this file's `#1`: `Src`/`SrcRel`/`..`-relative paths, `DirectEmbed`, conditional-load flags) **and rules it out as the texture-extension rewrite site** - the table has no extension string of any kind. `%s\%s` at `0078bf80` is worth checking against `SrcRel`'s directory-join behaviour (this file's rule `SrcRel resolves against the including file's directory`) - a real corroboration of that rule from the executable, not from data alone, if it's confirmed to be the join format. Not yet confirmed which of the object's fields it formats.
- `scripts/ps3-toc.py map`, grepped for HUD/Sprite/Image/Texture-shaped `.cpp` names, turned up the actual candidates for a HUD widget's own `src=` reader: `Image_Item.cpp` (`0x001b5c90`/`0x001b6270`/`0x001b7c18`), `ImageModel_Item.cpp` (`0x001b9148`/`0x001b94b8`), `PI_HUD_Item.cpp` (`0x001e4150`/`0x001e4230`/`0x006a1bd8`) and `Texture_Importer.cpp` (`0x002de488`/`0x002de528`/`0x002de5c8`/`0x002de898`/`0x006b52f0`). `Texture_Importer.cpp` is the class `FUN_00196180` (the track-emblem loader from the first pass) hands its already-built `.gtf` path to - decompiling its constructors (`0x002de5c8`/`0x002de898`) shows them interning an **already-fully-formed** path string into a resource cache (hash-bucket lookup keyed off the string, via `0x0032a8b8`), with no character-level extension logic at all. **Rules out `Texture_Importer` as the rewrite site too** - whatever builds the path happens before this class ever sees it.
- `Image_Item.cpp`'s and `PI_HUD_Item.cpp`'s constructors (all three read this session) only set up base-class wiring and default field values - no attribute-name string table the way `LoadXML_Item`'s did, meaning their actual attribute-parsing method is a normal virtual call the `__FILE__` trick doesn't reach (it only attributes constructors/allocators). Not chased further this session - vtables are at `PTR_PTR_008ad61c` (`Image_Item`) and `PTR_PTR_008ae9a8` (`PI_HUD_Item`), read with `inspect_memory_content` the same TOC-free way, but the entries are 8-byte-spaced small thunks (base-class boilerplate, per the `LoadXML_Item` vtable already read) rather than one obviously-named `Load`/`Parse` slot - would need each candidate slot disassembled to tell which is the attribute reader.
