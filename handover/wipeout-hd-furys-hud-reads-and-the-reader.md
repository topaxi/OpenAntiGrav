# Wipeout HD / Fury's HUD reads, and the reader it shares with Pulse was wrong in three ways Pulse's own data could never have shown

2026-08-17. All **eighteen** of HD's shipped HUD layouts compose with **nothing missing and nothing skipped**, into 2,320 widgets - cross-checked against a second walker written in the test file, because Pulse's `grep`-the-file trick does not survive a layout that is 17 files. `oag_hd::hud`, `oag_game::hud::compose`, `crates/game/tests/hd_hud_ground_truth.rs`, [hd-hud.md](../docs/formats/hd-hud.md). **HD's HUD is Pulse's HUD composed out of fragments**: a mode's root is a shell of 1-2 KiB that pulls in up to sixteen more by `<LoadXML SrcRel=... DirectEmbed="true">`, 720 of 720 includes on the disc spelled that way and none with `Src`. **Three rules, each of which Pulse's own five layouts are silent about.** (1) **`SrcRel` resolves against the including file's directory**, which is the only thing making the three skins distinct - `/data/xml/elimination_hud.xml` and `/data/xml/wo3_hud/elimination_hud.xml` both name `HUD_elim_line.xml` and mean different files - and **`..` ships**: Duel reaches four fragments as `..\HUD_colours.xml`, so a reader that concatenates loses a quarter of that mode's HUD with an error that reads like a missing file (5 files -> 9 once the segment is applied). (2) **`OffsetX`/`OffsetY` compose down the tree and `x`/`y` do not.** The walker read an `<Item>`'s offset as *absolute* on the stated grounds that "nothing in the shipped data nests them" - true of Pulse (26 offsets, all `<Item>`, 0 nested) and false of HD (218 offsets, 116 of them on widgets, 242 widgets holding widgets). (3) **A nameless widget is drawn, not broken.** Both widget readers required a `name` and recorded the loss in `skipped`; Pulse names all of its, HD leaves **106** anonymous against 2,214 named, mostly `BackgroundLayer="1"` panels behind a named readout. **And the layouts name source art rather than shipped files**: `hdHUD.mip` (148 sprites) and `detonator_hud2.tga` (44) are the two most-used references and neither extension exists on the disc - both resolve with the extension replaced by `.gtf`, so 12 of 12 references land instead of 10. `oag_hd::hud::texture_entry`, confidence 85, **no executable path read for it**. **One thing to know before continuing.** `docs/formats/hd-hud.md`'s counts are the composition *this build* performs: six of the eighteen roots ship in **more than one archive at different sizes** (`elimination_hud.xml` is 1,856 bytes in `DATA00` and 5,666 in `DATA02`), `oag_assets::Archives` picks by this project's own precedence, and **whether the original picks the same copy is unread** - the test pins it per root so a change to the archive order shows up there rather than in a screenshot. Both of this row's holds - no `.gtf` decoder, no pixel drawn - are discharged.

## Open

- Whether the original executable resolves HUD texture names to `.gtf` the same way (`oag_hd::hud::texture_entry`, confidence 85) is unconfirmed - no executable path has been read for it. **String search alone cannot answer this** (2026-08-25, below) - neither `hdHUD` nor `detonator_hud2` (the two literal source-art names that need the rewrite) exist anywhere in the executable's strings, only in the disc's XML, so any resolution happens against a value read at runtime, not a hardcoded table.
- Whether the original picks the same archive copy as this project's precedence, for the six roots shipping at different sizes in multiple archives, is unread. Not attempted this session - it needs the same runtime file-open/archive-mount tracing this row's other open question does, and is the same shape of unread question as `FRONT_END_PLUGIN_DEFINITION`'s five disagreeing copies (`crates/hd/src/lib.rs`).

## Next Steps

2026-08-25: spent ~45 min in `/ps3-hdfury-eu/EBOOT.elf` chasing the extension-rewrite question by string search, confirmed a negative rather than a mechanism, and stopped rather than guess. What was checked:

- `search_byte_patterns` for the raw bytes `2E 67 74 66` (`.gtf`) - every hit falls inside a full path string Ghidra had already defined (e.g. `Data\FE\Images\badges.gtf`). No hidden, un-defined `.gtf` literal exists anywhere else in the binary.
- A regex bare-context search (`[^.]gtf`, i.e. a `gtf` not preceded by a dot) turned up exactly one hit beyond the leading-dot path strings: `image/gtf` at `007a7e18`. Traced its one caller (`FUN_00328f70`, a trivial getter) up to its only caller (`FUN_002b86a0`), which is a large state machine referencing `"AdServer Not Found"` and driving `cellFsOpen`/`cellFsLseek`/`cellFsClose` - **PS3's downloadable-ad-content cache, not the HUD texture loader.** Dead end.
- Confirmed the two literal source-art names (`hdHUD`, `detonator_hud2`) are absent from the executable's own string table entirely (`search_strings` on both, zero hits) - they only exist in the disc's XML. This is the reason string search cannot find the rewrite even if it exists: whatever resolves it has to read the name out of the XML at runtime, not match against a compiled-in table.
- As one data point on how the executable *does* build `.gtf` paths at runtime: `FUN_00196180` (xref'd from the `%s\fe\miniBW.gtf` format string at `00789aa8`) builds the track-select emblem's path with `.gtf` **hardcoded directly in its own format string**, not by stripping and replacing an existing extension. Suggestive that the engine's pattern per-caller is "this call site always wants `.gtf`" rather than one shared `replace_extension`-style utility the HUD loader would also go through - but this is a different code path (track emblems, not a HUD layout's `src=` reference) so it's a lead, not confirmation either way. Left unnamed - not enough evidence yet to clear the 50-confidence bar for a rename, and it isn't itself part of this row's HUD question.

Next real step, for whoever picks this back up: **trace dataflow, not strings.** Find where a HUD layout's `<Item src=... />` (or the fragment loader's own path-building, since HD's HUD is composed from `<LoadXML SrcRel=...>` fragments per this file's `#3`) gets parsed at runtime, and follow that value forward to wherever it's turned into an archive/file open. That is the only way to reach a rewrite that operates on a runtime string rather than a compiled-in literal - Ghidra's `analyze_dataflow` / `get_function_pcode` starting from the XML attribute reader is the likely route, not another string or byte-pattern sweep.
