# A circuit's billboard slots are a 9-entry array on the engine side, and slot 7 is not what it says it is

2026-08-25, mechanism read at instruction level (capped 84, static-only per [visibility.md](../docs/ghidra/functions/ps3-hdfury-eu/visibility.md)'s own rule). Full account: [billboards.md](../docs/ghidra/functions/ps3-hdfury-eu/billboards.md). `TrackStartup_Load` (`0x000b19a8`, `Track.cpp`) parses `Num`/`Location`/`Color`/`Colour`/`Glow` per `<Billboard>` and stores each into a singleton's array at literally `array[Num]`, 1-8, index 0 wasted - confirmed two ways: `Billboard_CreateFromLocation_q`/`_FromColour_q` (`0x0029adf8`/`0x0029af88`) index it unadjusted, and its manager's constructor/destructor pair zeroes exactly nine words, matching the manifest's own comment, `"num" (1-8)`. **That kills "a node looked up by a name the engine builds"**: the two stray `Billboard<digits>` nodes on `02_track`/`05_ubermall` are artist debris. It **instantiates** rather than merely texturing existing geometry - `Billboard_ConstructResource_q` (`0x0029a6a8`) branches on the location's own `.vex`/`.mip` suffix and allocates a 0x2080- or 0x100-byte object; no manifest on the disc names a non-`.vex` location, so the `.mip` arm is implemented-and-unexercised, the same shape as the draw-order row's `0x31` branch. `type` is read nowhere in this function despite every one of 118 slots authoring it - unconsumed here, unread elsewhere. Checked against all 16 extracted manifests: none authors `Colour`, `Glow` or `<Render>`, so the parser is right to skip them; `<Render>` is a `<Billboard>` sibling this function recognises by name and then discards the comparison result outright - dead code in this build. **The new, surprising part**: `Billboard_CreateFromLocation_q` special-cases `Num==7`, not 8, and replaces whatever the manifest authored there (always `fx350.vex`, all 16 circuits) with a pointer read off a global mode-descriptor struct, when two of its fields are non-null. Four `321Go_*.vex` names (`StartFinish`/`Zone`/`HD_Zone_Battle`/`hd_detonator`) sit in the same TOC window and match the four known race-gate shapes by name, but the pointer was not traced all the way to one of them - a lead, not a finding. **Chased, partially**: `GetBillboardMeshIdFromName` still has no found caller - its only xref is a data reference into the module's ordinary `.opd` section, not a billboard-specific table as first thought (checked both sides: the descriptor pattern runs on well past any table-sized window). A separate, unnamed 4.5 KB function (confidence below 50) *is* reached for real, traced from `Billboard_ConstructResource_q` through a TOC trampoline, and inlines the same search-and-bind write against a same-shaped per-slot lookup: a repeated bind idiom, still resetting rather than positioning. If a caller exists it must use a 0-based index, not raw `Num`. No direct `bl` caller and no stored function pointer (validated against a control) - no known invocation path, not confirmed dead. Nothing placed.

2026-08-28, cross-title: **Pulse ships the same file, per circuit, and the parser silently found nothing on it until now.** `TrackStartup::parse` (`oag_formats::trackstartup`) called `fexml::parse` directly; that reads HD's plain XML fine but returns zero billboards on Pulse's `fexml`-shortened one, which needs `fexml::text` run first to expand the `<code>` dictionary - fixed, with a regression fixture. A second, independent bug in `oag-game`'s load report (`crates/game/src/race/load.rs`) looked for `/` to find a circuit's directory, which finds nothing on Pulse's `\`-joined paths even once the parser is fixed - also fixed, and both are covered by a new ground-truth test (`pulses_default_track_reports_its_own_trackstartup_xml`) and a real-disc `--dry-run` run against `16_Track`. Read directly off 11 of Pulse's 12 circuits (`26_Track` is `25_Track`'s `Zone` variant and carries no manifest of its own): **slot 8 is `321Go_StartFinish.vex` on every circuit that authors one billboard 8**, the same as HD - except `14_Track`, which authors *three* entries under `num="8"` (`Checkered_StartFinish.vex`, `Final_Lap_StartFinish.vex`, `321Go_StartFinish.vex`); `TrackStartup::billboard` returns the first, and which one the original shows when is unread. **"Slots 7 and 8 are reserved" does not generalise**: Pulse's slot 7 is a different model or colour on nearly every circuit, never `fx350.vex` (that name is HD-only, not on any Pulse manifest). Full table in `oag_formats::trackstartup`'s own "Cross-title: Pulse" doc section.

Also found while reading Pulse's disc for this: `Data\Plugins\PI004\Definition.xml`, a 35-entry catalogue of every billboard advert on the disc - name, `Portrait`/`Landscape`, `location`, and a space-separated list of colours the model supports. Every colour name any `TrackStartup.xml` authors also tags a `PI004` entry, which reframes a colour fill as a **pool selector** into this catalogue rather than a literal tint - plausible, not confirmed, since nothing has traced a function reading either side of it. `docs/formats/pure-status.md` independently found the same plugin id on Pure (excluded from the language picker, never read for content before now), so this is very likely a third title, not just Pulse.

**A cheap placement hypothesis was tried and killed, on purpose, before it reached the renderer.** `16_Track`'s own art mesh embeds five numbered placeholder textures (`billboard1/2/6/7/8.tga`, each an 8x8 icon of its own digit) on a handful of quads scattered through the track - see `docs/formats/vex.md`'s texture-stride section for how those were first found, and CLAUDE.md's "billboards by default just render an actual number" is that texture, seen live in this project's own renderer, not the original. Binding each slot to the placeholder quad wearing its number, using the quad's own world transform (`oag_formats::vex::world_transforms`, already available), was the obvious next move - and the manifest itself rules it out: `16_Track` authors all eight slots but only five numbers have a matching placeholder texture anywhere in the mesh. A mechanism that cannot place three of the eight slots it is supposed to explain is not the mechanism, so nothing was wired off it - the same shape of trap the `Billboard<digits>` node names above turned out to be.

2026-08-28, later the same day, **live PPSSPP trace: Pulse's own loader found, and "nothing is placed" is now a runtime-confirmed fact rather than a static inference.** Full account: `docs/ghidra/functions/psp-pulse-usa/billboards.md`. A halting read watchpoint on `%s\TrackStartup.xml` fired mid-circuit-load; walked live via exec breakpoints on each callee's `jr ra` (a stack-offset guess for one caller's return address gave a plausible but wrong value once - the breakpoint technique is the one to trust). The chain: `World_LoadTrack` -> `Xml_OpenFile` -> `TrackStartup_Parse` (`0x08884ac4`, reads the same six attributes this project's `oag_formats::trackstartup` does, `Color`/`Colour` merging confirmed live) -> `Billboard_CreateFromLocation_q`/`Billboard_CreateFromColour_q` (`0x089012d4`/`0x08901004`, both index a 9-entry array by raw `num`, same architecture as HD's) -> `Billboard_ConstructResource_q` (`0x08900220`, same `.vex`/`.mip` dual-branch, dual-size architecture as HD's `Billboard_ConstructResource_q`). **The shared constructor writes a 4x4 transform into every new billboard, and read live it is the literal identity matrix - the same sixteen floats regardless of `num`.** `num` only indexes the array and seeds three derived resource-tag IDs, never a position. All four functions renamed (`TrackStartup_Parse` 78, `Billboard_ConstructResource` 75, the two constructors 65/60 with `_q`) and added to `names.tsv`.

**One live lead survives, and it beats every HD-side lead on offer**: `Billboard_CreateFromColour_q` walks a per-track pool (`*(int*)(_DAT_002ae2b4+0x3c)`, count at `+0x40`) before constructing anything, matching entries by type hash and a colour bitmask, consuming the match. Confirmed *reached* during a real circuit load - not merely referenced, the failure mode `GetBillboardMeshIdFromName` on HD and `PI004` on Pulse both have. Its entries' own layout (what sits at their `+0x94` and neighbours) was not read; this, not `PI004`'s catalogue, is now the best next step if placement is chased further.

A second, unrelated trap surfaced walking the call chain: several call targets in `Billboard_ConstructResource` decompile as `func_0x00XXXXXX(...)`, a low pseudo-address `get_function_by_address` cannot resolve even though `docs/ghidra/workflow.md` records this binary's *data*-constant relocation wart as fixed. `real = pseudo + 0x08804000` (the binary's own image base) held for every case checked - reads as the `R_MIPS_26` (`jal` target) relocation not being applied even where `R_MIPS_HI16`/`R_MIPS_LO16` are. Noted in `workflow.md` itself; not chased further.

## Open

- The mode-descriptor pointer replacing `Num==7`'s mesh was not traced all the way to one of the four `321Go_*.vex` race-gate shapes.
- `GetBillboardMeshIdFromName` still has no found caller.
- The unnamed 4.5 KB bind function (confidence below 50) has no confirmed caller or invocation path - not confirmed dead either.
- `type` is authored by every one of 118 slots but is read nowhere in this function or elsewhere.
- **Pulse's colour-path pool** (`_DAT_002ae2b4+0x3c`, walked by `Billboard_CreateFromColour_q`) has not had its entries' own layout read - the single most promising placement lead either title has, because it is confirmed reached rather than merely referenced.
- `Data\Plugins\PI004\Definition.xml`'s colour-pool reading is a lead, not a finding: no function has been traced choosing an entry from it, and the live pool above is a more promising target than this catalogue.
- `14_Track`'s three `num="8"` billboards: which one the original actually shows, and whether `num` is really unique per Pulse manifest the way the HD comment insists, is unread.
- Whether Pulse's construction-time identity-matrix write is later overwritten by a draw-time placement step outside this call chain is unread - only construction was traced.
- The `func_0x00XXXXXX`/`jal`-relocation gap in `psp-pulse-usa` (above) is its own open item, scoped narrower than the fixed data-constant wart `workflow.md` already describes.
