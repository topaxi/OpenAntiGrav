# Wipeout HD / Fury's HUD reads, and the reader it shares with Pulse was wrong in three ways Pulse's own data could never have shown

2026-08-17. All **eighteen** of HD's shipped HUD layouts compose with **nothing missing and nothing skipped**, into 2,320 widgets - cross-checked against a second walker written in the test file, because Pulse's `grep`-the-file trick does not survive a layout that is 17 files. `oag_hd::hud`, `oag_hud::compose`, `crates/game/tests/hd_hud_ground_truth.rs`, [hd-hud.md](../../docs/formats/hd-hud.md). **HD's HUD is Pulse's HUD composed out of fragments**: a mode's root is a shell of 1-2 KiB that pulls in up to sixteen more by `<LoadXML SrcRel=... DirectEmbed="true">`, 720 of 720 includes on the disc spelled that way and none with `Src`. **Three rules, each of which Pulse's own five layouts are silent about.** (1) **`SrcRel` resolves against the including file's directory**, which is the only thing making the three skins distinct - `/data/xml/elimination_hud.xml` and `/data/xml/wo3_hud/elimination_hud.xml` both name `HUD_elim_line.xml` and mean different files - and **`..` ships**: Duel reaches four fragments as `..\HUD_colours.xml`, so a reader that concatenates loses a quarter of that mode's HUD with an error that reads like a missing file (5 files -> 9 once the segment is applied). (2) **`OffsetX`/`OffsetY` compose down the tree and `x`/`y` do not.** The walker read an `<Item>`'s offset as *absolute* on the stated grounds that "nothing in the shipped data nests them" - true of Pulse (26 offsets, all `<Item>`, 0 nested) and false of HD (218 offsets, 116 of them on widgets, 242 widgets holding widgets). (3) **A nameless widget is drawn, not broken.** Both widget readers required a `name` and recorded the loss in `skipped`; Pulse names all of its, HD leaves **106** anonymous against 2,214 named, mostly `BackgroundLayer="1"` panels behind a named readout. **And the layouts name source art rather than shipped files**: `hdHUD.mip` (148 sprites) and `detonator_hud2.tga` (44) are the two most-used references and neither extension exists on the disc - both resolve with the extension replaced by `.gtf`, so 12 of 12 references land instead of 10. `oag_hd::hud::texture_entry`, confidence 85, **no executable path read for it**. **One thing to know before continuing.** `docs/formats/hd-hud.md`'s counts are the composition *this build* performs: six of the eighteen roots ship in **more than one archive at different sizes** (`elimination_hud.xml` is 1,856 bytes in `DATA00` and 5,666 in `DATA02`), `oag_assets::Archives` picks by this project's own precedence, and **whether the original picks the same copy is unread** - the test pins it per root so a change to the archive order shows up there rather than in a screenshot. Both of this row's holds - no `.gtf` decoder, no pixel drawn - are discharged.

2026-08-25, sixth pass: the disc-side check this pass opened with turned out to answer the open question outright, without needing `0x00725938`'s class or the manifest lookup at all. **Correction first**: the previous pass's framing overstated its own conclusion - "a rewrite has to happen in the original's own code" is one licensed reading of the disc-side facts, but a build-time (packaging) reconciliation satisfies the same two facts just as well, and five negatives in a row (four classes, sixteen `cellFsOpen` callers) is what *either* explanation looks like from the executable side. What follows discriminates between them.

- **`FUN_00196180` corrected, not just re-read.** The prior pass's note that it "hands `Texture_Importer` an already-built `.gtf` path" is true but was read as more significant than it is: `scripts/ps3-toc.py resolve 0x00196180 -0xa6c` (module A, TOC-exact, so trustworthy without the inherited-TOC caveat) gives the format string outright - `'%s\fe\miniBW.gtf'`. This is a **hardcoded** ship-thumbnail path, built from a bare ship directory (`%s`) with a literal `.gtf` suffix baked into the format string itself. It does not read or transform any XML-authored name, so on its own it demonstrates nothing about a runtime rewrite mechanism - a future pass reaching for this function as "the rewrite site" is a dead end already spent.
- **But it is the key that unlocked the real answer.** Extracting the XML that names this exact asset shows `Data\Ships\<Ship>\fe\miniBW.tga` - the *same* game asset, authored with the *same* mismatched-extension shape as `hdHUD.mip`. The executable's own hardcoded convention for it: ignore the XML's extension entirely, always emit `.gtf`. That is direct evidence of what the engine's convention *is* for this shape of problem, even though it is one hardcoded instance and not the generic HUD code path.
- **The discriminating test, run project-wide**: every `Src`/`ImageSrc`-shaped attribute value across all of HD's XML (not just the HUD's twelve references) was extracted - `rg -o -I '="[^"]*\.(mip|tga|gtf|dds|bmp|png)"'` over every `.xml` file across all seven `DATA0N.PSARC` archives, `sort -u` - giving **133 distinct image references**. Each was normalized (backslash(es) to `/`, uppercased - matching `oag_formats::psarc::path_digest`'s own uppercasing) and its extension replaced with `.GTF`, then checked against the full-disc PSARC manifest (`psarc.py list`, no archive argument, all seven read). **129 of 133 (97%) resolve** - `hdHUD.mip` and `detonator_hud2.tga` both among the 129, not the 4 exceptions. The four that don't resolve (`Data\FE\Images\teaser_firedup.mip`, `teaser_medievil.mip`, `teaser_wipeout.mip`, `Data\Skins\Default\Images\default_texture.mip`) were checked directly against the manifest under every spelling and **do not exist on the disc at all**, under any name or extension - cut promotional content and an unbacked fallback name, independently explained, not counter-examples to the rule.
- **This settles the thread's central open question**: the rule is a blind, mechanical extension replacement - strip whatever extension the XML authored, append `.gtf` - applied uniformly regardless of what the source extension was.
