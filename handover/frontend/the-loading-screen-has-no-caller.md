# The loading screen draws now, and its wave is partly runtime-verified

The rippling band is procedural and the `loading` plugin holds no video; the decode is pinned against the real blob (which is **swizzled**, bit 0 of `+0x07`, and **fully opaque**, so both plausible wrong readings are excluded by construction). The "no caller" half is stale: `LoadingStage` (`crates/game/src/main/loading_stage.rs`) constructs `oag_render::loading::Pipeline` and calls `capture::draw_wave` on both the boot path and the pre-race path (`feat(loading): recover HD's loading screen, and put one before every race`, 2026-08-24), confirmed against the real disc via `loading_screen_ground_truth` (5/5). **Two of the motion model's three open claims are now runtime-verified, one only narrowly**: `scripts/psp-loading-wave-capture.py` predicted each column's internal state (`raw`/`disp`/`energy`) from the previous one and matched what `Loading_DrawWave` actually computed to float-rounding precision across hundreds of consecutive columns, plus one observed call boundary matching the reset-to-zero, phase advance and envelope-table indexing all at once (confidence 85 -> 96). `scripts/psp-loading-wave-emit-capture.py` then confirmed the *emitted* draw arguments match that state too (52/52 exact, confidence 85 -> 90) - but every one of those captures landed inside `x=0..14`, where the wave hasn't developed any real amplitude yet, so it confirms the wiring rather than the formula at a value that would expose a value-dependent bug.

## Open

- Neither internal-state capture happened to land on one of `g_loading_wave_envelope`'s two 99-peaks (`phase` was 1 then 2, both low entries), so the `pulse / 99.0 + 0.1` amplitude term is exercised structurally but not at its largest live value.
- All three emitted-argument captures stayed inside `x=0..14`. `layer0` versus `layer1` has never been distinguished either, for the same reason - both predict the identical `220` that early.
- A real, unexplained ceiling: every `psp-loading-wave-emit-capture.py` run stops within the same narrow band, about 130-140 total breakpoint hits (120 of them always the boot logo). `PPSSPPHeadless` is left running afterward, still burning CPU - the debugger connection stops answering, the process does not exit. Not a crash, not root-caused. See the doc page's own "Not determined" section and the script's docstring for the trap this cost to find (a breakpoint on already-JIT-compiled code silently does not take, which is why this capture has to arm from cold boot rather than chaining off `Loading_Show` the way the sibling script does).

## Next Steps

- Reaching a genuinely developed `x` (past ~150, per the internal-state captures) while *also* catching the emitted arguments needs either working around the ~130-140-hit ceiling above, or a cheaper substitute: since `psp-loading-wave-capture.py` already proves `local_70`'s own state is correct out to hundreds of columns, one option is a much shorter, targeted emit-capture that skips fewer boot-logo hits before reaching the wave (e.g. arm nearer the tip screen some other way that avoids the JIT-precompiled-block trap) rather than sitting through all 120 of them plus the wave's first columns in one continuous run.
- Once past that, run `scripts/psp-loading-wave-capture.py --hits` with a larger budget, or timed to start nearer a beat (the envelope wraps every 24 frames at 30 Hz, so roughly every 0.8 s an entry of 99 is live), to close the `pulse != 0` residual on the internal-state side.
- A fresh `PPSSPPHeadless` instance is required per run for both scripts, never a reused/already-probed connection - see either script's own docstring on why a leftover breakpoint from an earlier connection can silently defeat a new one.
