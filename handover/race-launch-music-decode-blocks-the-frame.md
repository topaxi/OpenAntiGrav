# Race-launch music decode blocks the frame thread for ~2.8s, held behind an already-faded loading screen

2026-08-25, branch `worktree-loading-fade-race-ready` (commits `bf343ce`..`2666576`). Three measured rounds chased a "loading screen fades too early, then a black gap before the race starts" report. First fix (eager `Stage::race` build, `bf343ce`) closed the CPU-side scene-build stall, but a fresh ~3s gap remained. A GPU pipeline-compilation warmup (`528838b`) was the next guess - measured at 84ms with zero effect on the reported number, so that hypothesis is retired. Finer timers (`2666576`) then isolated the real cost: `Audio::start_race_music`, called synchronously inside `Session::finish_race_loading` at the hand-off, decodes the whole race track on a cache miss before returning. Measured: `race music started in 2.829003119s` for a 195.8s PS2 track, while the first race frame's own render/submit/present took under 12ms combined. That is the whole of the remaining gap - confirmed by log ordering across two full re-runs, not a guess.

## Open

- The fix is designed below but **not implemented** - `Audio::start_race_music` -> `fetch_indexed` -> `load_track` -> `load_ps2_track` still runs on the frame thread at the race hand-off.
- Only the PS2 path was measured. The PSP path (`crate::music::load_entry`, the `_ =>` arm of `load_track`) is the same shape - a cold decode into memory - and likely equally slow, but that is inference, not a second measurement.
- Whether `RaceStage::warm_up` (`528838b`) is still worth keeping is open: it measured 84ms with no effect on the symptom, and its doc comment asserts a cause (deferred pipeline compilation) that further measurement did not support. Don't strip it before the audio fix is confirmed to close the gap on its own - losing the ablation would mean re-diagnosing from scratch if it turns out to matter after all.

## Next Steps

Mirror `race::LoadWorker`'s shape (`crates/game/src/race/worker.rs`) inside `crates/game/src/audio.rs`:

1. `Audio::locate` (`audio.rs:1164`) does not touch `self` in its body - drop `&self` and call it as a free function. This is what lets the decode run off the thread that owns the mixer.
2. Add `fn fetch_race_track(discs: &MusicDiscs, choice: MusicSource, cache_dir: &Path, index: usize) -> Result<Option<Loaded>>` as a free function: the `locate` + `load_track` half of `fetch_indexed`, deliberately without its "already read" cache check - a worker spawned before the race it is fetching for has no `Audio` state yet to check against. Make `struct Loaded` (`audio.rs:548`) `pub` (fields can stay private) so `RaceMusicWorker::join()` can return it across the `oag-game` lib/bin boundary, the same way `race::Loaded` already does.
3. Add `pub struct RaceMusicWorker { handle: Option<JoinHandle<Result<Option<Loaded>>>> }` with `spawn`/`is_finished`/`join`, copying `race::LoadWorker`'s three methods.
4. Add `Audio::reserve_race_music_index(&mut self, discs: &MusicDiscs) -> usize`, extracted from the first few lines of `start_race_music`'s body (the `if self.race_index.is_none() { ... }` block) - lets a caller reserve the index before spawning the worker, without fetching anything yet. Have `start_race_music` call it too, rather than duplicating.
5. Extract `play_race_track`'s `match self.fetch_indexed(...) { ... }` body into a private `fn apply_fetched_race_track(&mut self, index: usize, fetched: Result<Option<Loaded>>, seek: Option<f64>)`, so the synchronous path and the new worker path share the "apply a decoded track to the mixer" logic. `play_race_track` becomes a two-line wrapper.
6. Add `Audio::finish_race_music(&mut self, mut worker: RaceMusicWorker, discs: &MusicDiscs, choice: MusicSource, cache_dir: &Path)`: stop old voices exactly as `start_race_music` does, read `index` back off `self.race_index` (already `Some` from step 4's reservation), join the worker (already finished by the time this runs, so this never actually blocks), and call `apply_fetched_race_track`.
7. In `crates/game/src/main/loading_stage.rs`: add `pub(crate) music: Option<audio::RaceMusicWorker>` to `LoadingStage`, and fold it into `race_ready()`: `self.race.is_none() || (self.built_race.is_some() && self.music.as_ref().is_none_or(audio::RaceMusicWorker::is_finished))`. Same "the fade may not start until this is ready" gate `built_race` already got in `bf343ce`.
8. In `crates/game/src/main/stage.rs`: `Stage::race_loading` takes an extra `music: audio::RaceMusicWorker` parameter and stores `Some(music)`; `Stage::loading` (the boot path) sets `music: None`.
9. In `crates/game/src/main/session/load.rs`: `Session::launch_race` calls `self.audio.reserve_race_music_index(&self.music_discs)` and spawns `audio::RaceMusicWorker::spawn(self.music_discs.clone(), self.settings.audio.music_source, boot::default_audio_cache_dir(), music_index)` alongside the existing `race::LoadWorker::spawn`, passing the worker into `Stage::race_loading`. `Session::finish_race_loading` takes `stage.music.take()` and calls `self.audio.finish_race_music(worker, &self.music_discs, self.settings.audio.music_source, &boot::default_audio_cache_dir())` instead of `start_race_music` - keep a defensive fallback to the old synchronous call if `stage.music` is somehow `None`, the same defensive style the `race_voice` guard in `start_race_music` already uses.
10. Leave `--race`'s direct launch (`crates/game/src/main/app.rs`, no loading screen) on the synchronous `start_race_music` - there is no fade to hide the wait behind there, so threading it buys nothing.
11. Keep the diagnostic log lines this thread added (`race scene built in`, `race scene warmed up in`, `race hand-off`, `race music started in`, `first race frame: encoded/submitted/presented in`, `first race frame presented`) until `race music started in` reads near-zero on a re-run - that is the pass/fail signal, not a guess.
12. Once confirmed, revisit the `RaceStage::warm_up` question from Open above.

Not runtime-verified against a live window in this sandbox (see the `no-gui-windows-on-desktop` note): the next session needs a real run to confirm the fix.
