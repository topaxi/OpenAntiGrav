# `WowDownload_VerifyPackFiles`: the DLC download completion check

2026-09-15. Reached by re-running a 2026-09-04 investigation's own blocked
xref search, once `get_xrefs_to` started working on `psp-pure-eu`/
`psp-pure-usa` - see "The xref gap that pass hit is closed" below. Read
alongside
[`docs/formats/dlc-pack.md#pures-packs-decrypt-with-an-external-key-table`](../../../formats/dlc-pack.md#pures-packs-decrypt-with-an-external-key-table),
which documents the pack format this function gates access to.

## The xref gap that pass hit is closed

The 2026-09-04 pass found zero callers of `sceUtilitySavedataInitStart`'s stub
and zero callers of a known-must-be-called control
(`sceCtrlReadBufferPositive`), against both `pure-eu` and `pure-usa`, and read
that as a gap in how this project's PSP import-stub calling convention shows
up to `get_xrefs_to`. It was not a convention gap: it was the pre-2026-09-07
Allegrex relocation bug (`docs/ghidra/workflow.md`, "Why a PSP import silently
loses every relocation") - the same bug already fixed for `psp-pulse-eu`/
`psp-pulse-usa` that day. `docs/ghidra/workflow.md`'s own relocation table
already recorded both Pure databases as fixed too (111,269 entries for
`psp-pure-eu`, 111,698 for `psp-pure-usa`, both reading zero before the
patch) - that table is the decisive number the same page warns function
counts cannot be (`workflow.md`: "Function count is not a usable check...
treat it as an anchor, never a pass/fail"), so cite the relocation count, not
the function count, as the reason `get_xrefs_to` works now. What had not been
checked before this pass was whether that fix actually restored a working
xref on *this specific* stub, on both regions - it does, on the first try,
with no workaround:

```
psp-pure-eu:  resolve-psp-imports.py against data/extracted/psp/pure-eu/.../BOOT.BIN
              -> sceUtilitySavedataInitStart stub at 0x08a42798
              get_xrefs_to 0x08a42798
              -> From 08896e80 in FUN_08896e78 [UNCONDITIONAL_CALL]

psp-pure-usa: resolve-psp-imports.py against data/extracted/psp/pure-usa/.../BOOT.BIN
              -> sceUtilitySavedataInitStart stub at 0x08a42d0c
              get_xrefs_to 0x08a42d0c
              -> From 088979e0 in FUN_088979d8 [UNCONDITIONAL_CALL]
```

`FUN_08896e78` on `pure-eu` was chased three levels up (see below); its
`pure-usa` counterpart `FUN_088979d8` was not decompiled at all - not yet
confirmed to be the same feature, only found to exist. The productive lead
for this page was the download-file-set string below, not this stub.

**The stub addresses in the 2026-09-04 investigation's own text (`0x08a76dfc` for
`sceUtilitySavedataInitStart`) are `psp-pulse-usa`'s, not Pure's.**
`data/ghidra/psp-imports.tsv` is generated by `scripts/resolve-psp-imports.py`
and paired with `psp-pulse-usa` specifically (`scripts/apply-ghidra-names.py`'s
own `BINARY_PROGRAMS` mapping) - there is no committed Pure-addressed
counterpart. Pure's own stub sits at a different address entirely
(`0x08a42798` in `pure-eu`, confirmed by running the same script directly
against `data/extracted/psp/pure-eu/PSP_GAME/SYSDIR/BOOT.BIN`). Anyone citing
an import-stub address for Pure from that file was citing the wrong binary's
number; this page's addresses are all read directly from the Pure databases.

On `pure-eu` only, chasing `sceUtilitySavedataInitStart`'s one caller
(`FUN_08896e78`, a three-line wrapper -
`iVar1 = sceUtilitySavedataInitStart(param_1 + 0xc); return iVar1 == 0;`)
upward leads into a savedata dialog state machine (`FUN_088973c0` /
`FUN_08864f10`, a per-frame poll of a large static object at `0x08b114e0`)
that turned out to be Pure's **ghost replay / profile** savedata feature, not
the DLC download path - a dead end for this lead, left unnamed. (`pure-usa`'s
`FUN_088979d8` was not chased at all; presumed but not confirmed to be the
same feature.) The productive lead was the string table already cited in
the 2026-09-04 investigation.

## `WowDownload_VerifyPackFiles`

**Confidence 80.** Found from that investigation's own evidence: the
20-byte-stride string table at `0x08a76c4c` (`pure-eu`) it already cited for
`TEST.BIN` and `PI.WAD` now resolves one caller with `get_xrefs_to`, where it
never did before the relocation fix.

| Binary | Address | Evidence |
| --- | --- | --- |
| `psp-pure-eu` | `0x08955494` | decompiled directly, this page |
| `psp-pure-usa` | `0x08955b44` | decompiled directly, byte-identical logic, this page |

Decompiled body (`pure-eu`; `pure-usa` differs only in helper addresses and
data symbol names, confirmed by decompiling both):

```c
undefined4 WowDownload_VerifyPackFiles(void)
{
  // ... two front-end screen lookups to zero a progress bar ("WOW Download",
  // "WOW Download Cancel"), via Screen_FindElementByPath (0x088b595c, named
  // in names.tsv) ...

  sprintf(path, "msroot:%s/PI.WAD", g_download_root);
  if (!file_exists(path)) { show_screen("WOW Download", ...); return 0x1e; }

  sprintf(path, "msroot:%s/ICON0.PNG", g_download_root);
  if (!file_exists(path)) { show_screen("WOW Download", ...); return 0x1e; }

  sprintf(path, "msroot:%s/PARAM.SFO", g_download_root);
  if (!file_exists(path)) { show_screen("WOW Download", ...); return 0x1e; }

  sprintf(path, "msroot:%s/PIC1.PNG", g_download_root);
  if (!file_exists(path)) { show_screen("WOW Download", ...); return 0x1e; }

  sprintf(path, "msroot:%s/TEST.BIN", g_download_root);
  if (!file_exists(path)) { show_screen("WOW Download", ...); return 0x1e; }

  // all five present: show "WOW Download Check" / "Overwrite Download",
  // with the pack's own name and size (%dKB) filled in
  return 0x1f;
}
```

`file_exists` is `FUN_0889e308` (`pure-eu`) / `FUN_0889ef64` (`pure-usa`) -
decompiled on both, byte-identical bodies, an open-for-check with no read of
the file's content. The `pure-eu` address also matches the same "does this
resolve" helper `docs/ghidra/functions/psp-pure-eu/race-box-screens.md`
already identifies in a different call chain (independent corroboration this
is a generic file-probe primitive, not something specific to savedata or
DLC). Two front-end screens are involved: "WOW Download" (shown
while a file is missing, error code `0x1e`) and "WOW Download Check" (shown
once all five are present, prompting "Overwrite Download" with the pack's
size, code `0x1f`). `"WOW HomePage"`/`"WOW Menu"`/`"WOW Redirect"` sibling
strings in the same table confirm `WOW` is this binary's own screen-name
prefix for Pure's embedded-browser online portal
(`psp-pure-eu/names.tsv`'s note that "Pure embeds a web browser"), not
something this page is naming - the prefix is kept as evidence, not invented.

**This is measured against the pack's own zip, not inferred from the string
table alone**: `unzip -l "data/dlc/WipEout Pure - Gamma Pack 1 (Europe) (DLC).zip"`
lists exactly `ICON0.png`, `PARAM.sfo`, `pi.wad`, `PIC1.png` and `TEST.bin` -
five files, no more, no fewer - matching this function's five checks name for
name, case differences aside (PSP's `msroot:` filesystem is
case-insensitive). `docs/formats/dlc-pack.md`'s "`PARAM.sfo` + `pi.wad` pair"
framing is about which two files carry decodable game content, not the whole
download; `ICON0.png`/`PIC1.png` are cosmetic (icon, screenshot) and `TEST.bin`
is this function's own completeness marker - all three are real files in
every shipped zip, just not ones `oag-wad` or the pack format itself needs to
read. Confidence 80 rather than higher because the file-set correspondence
and control flow are unambiguous, but this pass did not capture the flow live
in PPSSPP (no breakpoint/trace confirming the download actually runs this
function against a real network transfer).

## What this settles for the open thread, and what it does not

- **`TEST.bin`'s role is now a completion sentinel, not a signature input, at
  this call site**: `WowDownload_VerifyPackFiles` only ever asks whether
  `TEST.BIN` exists, never opens it for content. This is evidence against (not
  a disproof of) the savedata-signature hypothesis for `TEST.bin`'s 16
  high-entropy bytes - the code that manages this exact download bundle
  treats the file purely as a presence marker. If something does read
  `TEST.bin`'s content, it is a different call site than this one, still
  unlocated.
- **The trailer key is not here either.** No 16-byte buffer, XTEA constant, or
  key-sized literal appears anywhere in this function or its two file-probe
  helpers - it is pure path composition and existence checks. The
  `SceUtilitySavedataParam.key[16]` hypothesis
  (`docs/formats/dlc-pack.md`'s "still unknown" bullet) is untouched by this
  finding either way; it was never reached on `pure-eu`, because that
  region's caller chain from `sceUtilitySavedataInitStart` goes to the
  ghost/profile feature instead (see above), not to this download check.
  `pure-usa`'s equivalent chain was not traced.
- **The technique that unblocks further digging**: use `get_xrefs_to` directly
  against `psp-pure-eu`/`psp-pure-usa` addresses read from that binary's own
  extract (`resolve-psp-imports.py` run against
  `data/extracted/psp/pure-eu/...`/`pure-usa/...`, not against the committed
  `psp-imports.tsv`, which is `pulse-usa`'s). The workaround the earlier
  investigation was waiting on does not exist any more; the search was
  blocked by a bug that is now fixed project-wide on both databases.

## Open

- Where `TEST.bin`'s 16 bytes actually get read, if anywhere in `BOOT.BIN` at
  all - not found this pass. It may not be game code: neither `BOOT.BIN` nor
  Pure's PRXs import any NpDrm or KIRK primitive
  (`docs/formats/dlc-pack.md`), so a real PS Store download's content
  validation could be entirely system-side, in which case there is no
  in-game call site to find.
- The 256-byte trailer's own key: still unlocated, now reachable by direct
  `get_xrefs_to` search rather than blocked by the relocation bug - not
  attempted this pass beyond the one lead above.
