2026-08-19, on branch `worktree-rpcs3-harness`. `rpcs3 --headless --no-gui data/images/hdfury-ps3-eu-dec.iso` reaches HD's own loading screen in ~30 s with no window, printing the game's `printf` output to `~/.cache/rpcs3/TTY.log` - the free observability channel on this platform, and one the PSP side has no equivalent of. A stock `config.yml` already exposes a GDB stub on `127.0.0.1:2345` with `Debug Console Mode: false`; [`scripts/rpcs3_debugger.py`](../../scripts/rpcs3_debugger.py) speaks it. **Guest addresses are the ELF's own, unrebased** - `m10000` returns the decrypted EBOOT's ELF header - so every row in `names.tsv` is usable as typed. Memory read and write both work (write honours page permissions: `E03` on read-only, `OK` and readable back on writable). **Input has no API at all, and the two things that replace it both fail silently** - which is why [`scripts/rpcs3_pad.py`](../../scripts/rpcs3_pad.py) leads with a preflight (`just rpcs3-preflight`) that names the fix for each. Gate 1: `/dev/uinput` is `0600 root:root` until a udev rule says otherwise, so a harness dies on a bare `PermissionError`; `/etc/udev/rules.d/99-uinput.rules` with `KERNEL=="uinput", GROUP="input", MODE="0660"` is the persistent form and is installed on this machine as of 2026-08-19. Gate 2, the one that looks like a broken pad: with no `input_configs/global/*.yml`, RPCS3 logs `Input configuration empty. Adding default keyboard pad handler` and binds a keyboard that `--headless` has no window to feed, so every press vanishes with no error anywhere - three lines naming `Handler: Evdev` and the device fix it and RPCS3 fills the rest from defaults (`just rpcs3-input-config`, selected with `--input-config oag`). **A race now launches and drives, scripted, with no window on anyone's desktop** - `just rpcs3-race`, which is [`scripts/rpcs3-drive.py`](../../scripts/rpcs3-drive.py). Three things had to be true and only one of them was input. **First, `--headless` is a dead end for the front end and fails in the shape of a different bug**: the null renderer boots, prints as far as `TROPHY: Checking free disk space`, and stops for good with the main thread parked inside `cellGameDataCheck` while the process burns 200-330 % CPU - twenty scripted presses over four minutes changed nothing, and `Use native user interface: false` did not help. It is a boot-and-read-memory mode, nothing more. A **real renderer on Xvfb** reaches `Main Menu` in ~45 s; the Xvfb must be started `-listen tcp -nolisten unix` and addressed as `127.0.0.1:77`, because a sandboxed session cannot write `/tmp/.X11-unix` and then RPCS3 exits with `could not connect to display` while the *previous* run's `TTY.log` sits there looking like a fresh stall. `QT_QPA_PLATFORM=xcb` and dropping `WAYLAND_DISPLAY` are needed too. **Second, `TTY.log` is the state channel**: HD logs `Switching Screen "A" to "B"` on every front-end transition, which is the whole state machine for free - and it goes *quiet* during a race, so a driven lap is observable by screenshot and not by TTY. **Third, the walk is six taps of cross** with no d-pad at all (`Main Menu` -> `Campaign Selection` -> `Grid Selection Fury` -> `Cell Selection` -> `Team Selection` -> `Launch Game` -> `InGame`), then thrust held on `cross`. Verified end to end: Talon's Junction, lap 1/3, shield 100, ship visibly further down the track between two frames 8 s apart. Screenshots come off the virtual display with ImageMagick `import -display 127.0.0.1:77 -window root` and are *real frames, not black* - which is worth saying because the wgpu/Xvfb path on this same machine gives black. **Savestates were tried end to end and rejected**, for the same shape of reason the PSP `.ppst` was: creating one is a pad walk through RPCS3's *own* home menu overlay (the PS button opens it; `xdotool key` reaches nothing on this display, focused or not, and `windowclose` does not close the window either), which needs a display taller than 720p or the nine-item list is cut at six and `SaveState` is invisible - `up` three times from the top is the safe way to it, since the list wraps and `Exit Game` is adjacent. It needs `Suspend Emulation Savestate Mode: true` **and** `Compatible Savestate Mode: true` (without the second, capture dies on `Verification failed (object: 0x0)` and leaves an **empty** `savestates/BCES00664/` directory that reads as success to anything checking for the directory rather than a file), and `Save Disc Game Data` must stay `false` or the file goes 44 MB -> 2.0 GB and then refuses to load with `HDD0 deserialization failed: Invalid directory name`. The one that works loads in ~60 s and restores to HD's **Campaign / Event 01/08 screen, not the grid** - slower than the 45 s boot and no closer to a race, so it is not adopted. The overlay being pad-drivable is the finding worth keeping, and **`Start/Stop Recording`, two rows from `SaveState`, is the payoff**: `just rpcs3-record --drive 45` captures the driven part as 1280x720/30 fps MPEG-4 with **HD's HUD in the frame** - lap, position, lap time, shield and km/h - so a recording reads as a 30 Hz trace off the screen rather than just a picture, which is the closest thing to M3's per-tick capture this platform has. Two things to know: the file lands under `recordings/<TITLE_ID>/`, a **subdirectory per title**, so globbing `recordings/*` finds nothing and reads as silent failure; and `recording.yml`'s stock `AVCodecID: 12` makes RPCS3 match the `rtp_mpegts` output format, so the file is an **MPEG-TS stream with a `.mp4` extension** (ffmpeg reads it fine; `AVCodecID: 27` would land on real mp4, and that file is the user's, not the repo's). **The menu walk had to be rewritten to key on the screen rather than count presses**: HD runs at ~9 fps here and a `cross` landing mid-transition does nothing, so a fixed six presses ends on `Team Selection` about a third of the time - `Session.press_until` watches `TTY.log` for the expected screen and re-presses up to four times. **The HUD reads back as numbers, sparsely** - [`scripts/rpcs3_hud.py`](../../scripts/rpcs3_hud.py) (`just rpcs3-speed <recording>`) gave **63 samples over 788 frames at 15 Hz - 8 % coverage - spanning 225-444 km/h** with a mean frame-to-frame change of 4.3 km/h, every surviving value physically coherent. The design point is that the other 92 % are *gaps*: an earlier version without the right-alignment check read 28 % of frames and emitted `35` between `353` and `355`, and `747`, so coverage was traded for trustworthiness deliberately. Three structural limits, only the last of them tuning: the HUD is **alpha-blended**, so over bright track the strokes barely clear the background (a global threshold reads 13 %; the high-pass used here is what makes any of it work); the numerals are **right-aligned in a fixed field** - last digit's run ends at column 53 in 100 frames of 111, pitch 13 - which is the only thing that distinguishes a dropped digit from a real number; and the **template set is what one clip contained**, 0/2/3/4/5/7/8 and never a 1, 6 or 9. What would fix coverage is not more tuning: a **darker circuit** (Talon's Junction is the brightest on the disc), or the value the engine holds, which is a memory address reachable through `rpcs3_debugger.py`. **The first runtime reading on the PS3 binary landed, and it is a negative**: mid-race, `holder 0x008a6814 -> race manager 0x0095ae78` reads back exactly as [race-manager.md](../../docs/ghidra/functions/ps3-hdfury-eu/race-manager.md) describes - the first claim on this binary with a runtime leg rather than a decompilation-only one - but the base object's first `0xc000` bytes are **byte identical** across 25 s of real racing (the two frames differ by 0.364 RMSE, so the game certainly advanced; 0 of 12288 words changed). Craft dynamics are not in the RaceManager base object. Confidence 85, and the derived fields are **covered** rather than excluded: the indices are into a word array, so index `0xb8e` is byte `0x2e38` and `0xc000` reaches word index `0x3000` - the dump spans base and derived together, four times over. What it cannot rule out is a subclass running past `0xc000`. **`Z0` breakpoints fire - settled 2026-08-19, the confidence-35 hold is closed.** Under `PPU Decoder: Interpreter (static)` a breakpoint at `Collision_ProcessPairs` (`0x00038428`) stopped the main thread mid-race with a full register set (`lr = 0x000f88c0`, the unnamed caller one frame up), and another run stopped in `FwMutex_Lock`. Under the default LLVM recompiler they never fire *and the stub still answers `OK`*. **The expensive trap, found 2026-08-20 and the reason two readings above were wrong: RPCS3 parks a thread at a `Z0` breakpoint without ever sending a stop reply for it.** `wait_for_stop()` then blocks to its timeout and reports nothing, which reads exactly like "this address never executes" - a breakpoint on `Physics_StepWorld` (`0x000f8610`) returned nothing across 90 s of a screenshot-confirmed live race (lap 1/3, clock running, thrust held), and arming `FwMutex_Lock` in the *same* session stopped in 0.04 s and showed thread `01000000` had been sitting at the physics breakpoint the whole time. **A negative from `wait_for_stop()` is not a negative**; ask "is any thread's PC here" instead, which means stopping the target first - `Debugger.wait_at()` arms, resumes a slice, pauses and walks every thread. Two claims written earlier in that session died to this: that the `Collision_*` functions are "contact-gated, not per-frame" (separately ruled out by the disassembly - `bl 0x00038428` at `0x000f88bc` is straight-line, so pair processing runs on **every** physics step), and that the physics tick does not run during a race. **Breakpoints do re-arm** - three consecutive `FwMutex_Lock` hits, 0.04 s each, resuming between them without touching the breakpoint - so re-arming was never the problem; what does break is arming after an interrupt-pause with stop replies still queued, so **arm on the attach-pause** (drive the pad into position first, attach last) and `drain()` generously, since a breakpoint on a function several threads run queues one stop reply per thread and the next memory read then consumes one as its answer. **The craft bodies are found.** `Collision_ProcessPairs`'s caller is the physics step: `Physics_TickWorld` (`0x000f8a88`) guards one tick per frame against a global frame counter, clamps the delta at `1/15` (`0x3d88850a`) and steps at a fixed `1/60` (`0x3c888723`), then `Physics_StepWorld` (`0x000f8610`) walks an **inline** body-pointer array at `world+0x48` with the count at `world+0x2c8` (so at most 160 entries; the pointers are 4-byte words and read as 8 give nonsense). Live in a race: **count 8, in a race with eight craft**, every entry carrying the same `17.333 / 24.000 / 17.333` diagonal at `+0x010 / +0x024 / +0x038` - a 4x4 matrix based at `+0x10` whose constant diagonal is a per-body extent. Confidence 75 that this is the craft array; no body is tied to the player yet. **The big moving floats are not speed** - they run in both directions across a thrust-held interval, spread 87-545 across eight craft on one track, and `entry+0x200` equals `inner+0x0d0`, so they are two copies of a transform. The world pointer is **not** static (`0x3056cea0` one boot, `0x3056cda0` the next), so breakpoint-and-poll is the anchor. See [physics.md](../../docs/ghidra/functions/ps3-hdfury-eu/physics.md). **The address-space map was wrong and is now measured properly**: during a race 32 of 256 16-MiB slices answer - `0x01000000`, `0x10000000`, **`0x30000000..0x36ffffff` (112 MiB, the game heap - every pointer the physics breakpoint handed back lands there)**, `0x40000000..0x45ffffff`, `0x50000000`, and `0xc0000000..0xcfffffff` (RSX local). The earlier "~26 MiB" reading came from probing only the first 512 MiB, which **misses the heap entirely**. At the stub's **13.2 KiB/s** a blind scan of the heap alone is ~2.4 hours, so pointer-chasing from a breakpoint is the route and a scan is a last resort. Also ruled out: the savestate as an offline memory image - it does **not** contain the EBOOT's read-only pages, so there is no ELF header to anchor file offsets to guest addresses with. All eight bodies were then dumped whole and the analysis moved offline (the dumps stay out of the repository - guest memory is game content). **Body 7 was the player, and `entry+0x4c4` is engine thrust - confidence 85.** Driving a *pattern* is what settled it: two cycles of three samples thrusting and three coasting, twelve in all, every float offset of every body scored against the input signal. One field of one body came out and it is not close - body 7 `r=+0.942`, thrust mean **77.25**, coast mean **0.73**, against `r` between `+0.04` and `+0.53` and a flat 90-120 for the other seven, who are running their own engines. That is the direct confirmation the array was missing, so **the craft reading goes to confidence 88**. The player's index is not fixed across races. Two negatives are worth keeping because both looked like results: **braking is not a usable manipulation** (cutting thrust and holding both airbrakes put the craft into a wall, shield `100% -> 0%`, and the body that stood out was as easily carrying a contact impulse), and **six samples cannot correlate anything** - a six-sample run scored `entry+0x068` on body 2 at `r=-0.987` and looked unarguable, and at twelve samples the same body and offset scores `r=-0.040`. Of the entry's 320 words, 229 are byte-identical across all bodies and samples, 80 move, 11 are constant per body. **Speed is not in the bytes dumped**: re-scoring the same twelve samples against a leaky integral of the throttle at three decay rates put nothing in body 7 above `|r| = 0.85`, and against the square wave `+0x4c4` is alone at `0.942` with the next field down at `0.591` - so no speed scalar lives in the entry's first `0x500` bytes or the inner object's first `0x200`. **The multiple-comparison arithmetic is what makes the throttle finding safe**: 748 of the dumped fields varied enough to be scored, so a `|r| >= 0.80` threshold expects ~1.3 false positives by chance - at `r = 0.942`, `p = 4.7e-6`, expected false positives over 748 tests is **0.00**. **Steering is a candidate and not a result**: the same method against the airbrakes (thrust held, left for three samples then right for three, twice, so the craft wanders instead of walking into a wall) put one field over the line, `entry+0x284` on body 7, signed with the brake direction - but `r = 0.834` over 735 tests is `p = 7.6e-4` and **0.55 expected false positives**, a coin flip. What lifts it is that it landed on body 7, independently confirmed as the player in that same run by the throttle field being depressed to a mean of `66.32` against `82.72`-`101.83` for the other seven. **Twenty-four samples then refuted it** - nothing above `|r| = 0.80` on any body in either object, so `entry+0x284` was the coin landing heads and **no steering field is identified**. That run confirmed the player a third time and independently of any correlation (throttle mean `62.65` for body 7 against `97.87`-`106.40`), and it turned up something else: it ran long enough for accumulated wall scrapes to **destroy the craft**, and the body count went `8 -> 27 -> 23 -> 23 -> 21 -> 8` as the wreckage became physics bodies and the craft respawned. So **`world+0x2c8` is not the grid size** - it is 8 in steady state, which is what made it such good evidence, but it must be re-read every sample - and **craft hold stable low indices while transients append above them**, since index 7 separated cleanly across all twenty-four samples including the 27-body ones. **The craft class is now open, and reading four bytes split it without any statistics**: each body's `*entry` carries its vtable at `+0x0`, and it is `g_CraftVtable` (`0x008636e0`) for indices 0-7 and `g_DebrisVtable` (`0x008638e8`) for 8-26, never mixed - independent confirmation of the craft/debris split. Vtable slot `+0x3c` resolves to **`Craft_IntegrateHull` (`0x000ef450`)**, the per-frame integration: AltiVec throughout, four near-identical blocks each advancing a hull point at `craft+0x120`/`+0x130`/`+0x140`/`+0x150` by a shared vector at `craft+0x240` and calling `0x000364c0` - four hull points and four queries a step, which is what a hovering craft with four suspension points needs. **The craft object runs to at least `0x360`**, which is why the first pass found nothing: it dumped `0x200`. Dumping `0x600` produced the best field yet - **`craft+0x30c` is the throttle input, `r = 1.000`, and the values are exactly `100.00` and `0.00`** rather than merely correlated, which is a digital button written as a percentage. Confidence 90. With it came `craft+0x340` (mirrors `entry+0x4c4`, the thrust force, sampled a moment apart), and **game-time clocks at `craft+0x308`/`+0x320`/`+0x324`/`+0x348`** that rise ~3.8 a sample regardless of throttle. The run also reproduced `entry+0x4c4` on a **third** boot at `r = 0.935`, so that finding rests on three independent races. **Speed is not stored in either object**, on three scans: every scalar against the throttle pattern, every three-float vector *magnitude* (so it is not a velocity whose components each look like noise), and a correlation-free scan for the shape a speed must have - staying above a quarter of peak while coasting rather than zeroing, higher under throttle, falling through each coast run. Zero matches in the entry's first `0x500` or the craft's first `0x600`; everything that responds collapses to near zero off-throttle, which makes it a force. The likely answer is that the HUD's km/h is computed at draw time from a velocity the renderer reaches elsewhere. `0x000364c0`, the per-hull-point query, is **`Collision_MarchSegment`** - Ghidra stops its body at `0x000364e3`, and disassembling past that shows it take the segment between the hull point and the query point, compute its length with `vrsqrtefp` plus a Newton step, divide by a tuning constant and `fctidz` to a step count, and walk the segment in that many equal steps, returning a hit byte into the `craft+0x2b4` array. Confidence 72: the marching is not in doubt, the `Collision_` prefix is the inference, resting on its literals sitting within `0x50` of the `Collision.cpp` string slot at `0x008a5ec8`, which is how the linker groups a compilation unit's TOC entries. Five functions call it, so it is shared machinery. Next: the other three craft vtable slots (`+0x38`, `+0x40`, `+0x44`), and the velocity - which `Collision_MarchSegment`'s caller must hold, since `craft+0x240` is the vector every hull point advances by each step. Then a committed input script and a lap (wall-clock paced, **not** frame-exact - there is no cycle counter to key on). **Three findings that shape any harness built on this**: the stub answers *nothing but an interrupt* while the target runs - an `m` after `vCont;c` gets no reply at all, so a polling client hangs rather than paying PPSSPP's 520 ms; 41 ms a packet is the **paused** cost, giving ~24 operations a second, so there is no per-tick capture on this transport and an M3-equivalent trace harness is a further step not costed here; and `Z0` breakpoints do fire under the interpreter, but only ever tell you so if you poll thread PCs rather than wait for a stop reply. All 14 threads `qfThreadInfo` lists hold identical PCs across a 1 s and a 10 s window of real running (measured twice, with interrupt and resume separately confirmed), which reads at confidence 65 as PPU threads parked in HLE waits while the 200-330 % CPU the process burns is RSX/SPU work the thread list does not cover.
