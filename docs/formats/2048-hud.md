race shows is captured, the shield fill draws (cropped, thresholded and

## Four skin sets, and only one is played

The archive ships 26 `*_HUD.xml` documents: the same eight bare-root files HD
carries (`Arcade`, `Detonator`, `Duel`, `Elimination`, `MPTag`, `SpeedLap`,
`TimeTrial`, `Zone`), plus one skin set each under `2048_hud\`, `wo3_hud\` and
`2097_hud\`, plus one split-screen Zone file excluded on the same terms HD's
own is.

| Skin | Files | Referenced by any race-construction code found? |
| --- | ---: | --- |
| `2048_hud\` | 7 | **yes** - every real mode |
| bare root | 8 | yes - `DemoRaceManager_Construct` only |
| `wo3_hud\` | 5 | no matches found |
| `2097_hud\` | 5 | no matches found |

**Which skin a race reads is no longer a guess.** Four race-manager
constructors in `eboot.elf` hard-code a `2048_hud\` path directly:
`SpArcadeRaceManager_Construct` (Arcade), and three further ones for
Elimination, Zone, and a fourth that branches between `SpeedLap_HUD.xml` and
`SpeedLap_TimeTrial_HUD.xml` on a runtime flag - **time trial and speed lap
are two distinct files on this title**, unlike either PSP disc, which shares
one file between the two modes. `DemoRaceManager_Construct` is the one
function found that reads the bare root set, and it is the attract-mode demo,
not a race a player starts. Searching the executable's string table for
`wo3_hud` and `2097_hud` (both, as substrings) returns **zero** matches -
those two skins ship in full and compose cleanly, and no code path referencing
either has been found. See
[race-hud-selection.md](../ghidra/functions/vita-2048-eu-v104/race-hud-selection.md)
for the decompiled evidence, including the one confirmed miss in
`search_strings`'s own coverage that keeps "zero references found" short of
"proven unreachable".

## The coordinate-space tell

Every layout that authors a reticle names the same six `MissileSight*`
widgets [HD's own does](hd-hud.md), and the `2048_hud` skin's centre them at
`(-480, 272)` where the root/`wo3_hud`/`2097_hud` skins centre them at
`(-960, 540)`. Both are the shared placeholder idiom `oag_title::hud::Sights`
documents - a widget centred on the negated half of its own authoring screen
- and the two numbers are the Vita's native 960x544 and HD's own 1920x1080,
respectively. So three of the four skins are still authored for a screen this
title does not have, corroborating the code evidence above independently: the
one skin drawn at this console's own resolution is the one the code
constructs races from.

## Speed lap and time trial are different files here

`oag_title::HudLayouts` already models the two modes as separate fields
because HD needed them to be - both PSP discs ship no `SpeedLap_HUD.xml` at
all and reuse the time-trial layout, which is why five layouts serve six
modes there. 2048 is the opposite kind of evidence for the same axis: it ships
both files **and** a runtime branch that picks between them
(`Data\XML\2048_hud\SpeedLap_HUD.xml` vs
`Data\XML\2048_hud\SpeedLap_TimeTrial_HUD.xml`), so the two modes are
authored, composed and selected as genuinely separate HUDs.

## The reticle: concentric sprites, not `<Mode3D>` models

Zero of the 25 composed roots author a single `<Mode3D><Model>` widget - the
PSP titles' bracket-and-box reticle does not exist on this title at all. Every
layout that has a reticle authors it the way HD does: `<Image>` sprites named
`MissileSightBG`/`Outer`/`Inner`/`Middle` (seeking) and
`MissileSightLockedOnLines`/`Middle` (locked), plus a parallel
`LeachBeamSight*` family this axis does not model (`oag_title::hud::Sights`
carries one reticle, and HD's own `ART` leaves `LeachBeamSight*` out on the
same terms). Recovered from this title's own composed data, not carried over
from HD by analogy - see `crates/2048/src/hud.rs`'s doc comment on `ART` for
the full reasoning.

## The texture extension bug this pass found and fixed

`crates/2048/src/hud.rs` carried `TEXTURE_EXTENSION: &str = "gxt"` - missing
the leading dot - since the field was added. `oag_title::hud::replace_extension`
builds `format!("{stem}{extension}")`, so every reference on this title
resolved to a mangled name like `missile_reticulegxt` and no HUD texture
lookup on 2048 could ever have succeeded. Composing was never run against real
data until this pass, which is how a bug breaking every texture reference on
the title went unnoticed since it landed. Fixed to `".gxt"`; all nineteen
distinct texture references across the 25 composed roots now resolve.

Nine of the nineteen are the HD-inherited `.gtf`/`.mip`/`.tga` spellings
[hd-hud.md](hd-hud.md#the-layouts-name-source-art) documents - `2048_hud`'s
own five references are already spelled `.gxt` in the layout, so the rule is
a no-op on those and a real rewrite on the other three skins'.

## `.gxt` decodes now: `UBC2`, on a Morton-tiled block grid

**New format, [`gxt.md`](gxt.md) - the full evidence lives there.** The short
version: `oag_texture::gxt` reads the Vita's texture container, swept against
9,910 files in the base package with all parsing and the 370 `UBC2` (BC2)
ones decoding - which is every texture `2048_hud`'s own HUD reaches. The
block grid turned out to be twiddled (Morton/Z-order) rather than raster,
measured by decoding both ways and looking at the picture: twiddled,
`missile_reticule.gxt` and `hud_2048.gxt` render as real, recognisable
WipEout HUD art rather than noise. Wired into `oag_hud::sprite::Image::decode`
as a fourth branch, so a 2048 HUD sprite reference that resolves decodes to
real pixels through the same `Sheet` every other title's HUD uses.

## `EnergyBar` is wired: a vertical crop from the bottom (2026-09-20)

**The shield fill draws now, in its authored colour.**
`oag_hud::draw::crop_vertically` is the vertical counterpart to
`crop_horizontally` (Pulse's `ShieldBar` model): it shifts both `rect`'s and
`uv`'s `y` origin down by the cropped-away height and shrinks both heights by
the same amount, so the visible strip stays anchored to the silhouette's
foot rather than its crown. `EnergyBar` joins `oag_2048::hud::ALWAYS_ON`
(five names now, not four) and is cropped every frame to
`Readout::shield_fraction()`, the same reading `ShieldBarText`'s `%` already
used.

**Checked against the running original, not just against the layout.** A
fresh Vita3K-equivalent frame was not needed for this: `just play 2048
--race --mode single_race` at full shield, cropped to the shield icon and
compared 1:1 against `21-race2-start.png` (both 100%), matches in shape,
size and position exactly - the only difference is colour, covered below.
The crop's *direction and magnitude* are checked independently against
`36-w-5.png` (95%): the formula predicts the white/grey boundary at
`y = 372 + 110*(1-0.95) = 377.5`; the frame's own pixels (sampled down the
bar's centre column) turn solid white at row 377 - a match to within one
row. The same check on `68-zone-5.png` (27%, predicted boundary `y ≈
452.3`) lands a few rows off (white starts near 456), which is inside the
noise this column carries in Zone mode - a darker overlap not present in the
95% sample - rather than a sign the formula is wrong at low fill; the 95%
match is the cleaner of the two and the one to trust. Comparison images are not kept in the repository: the 3x shield comparison is
the side-by-side crop.

**Chosen, not measured: `EnergyBar`'s own runtime colour.** The layout
authors it green at half alpha (`[0.19, 1.0, 0.19, 0.50]`); the frames show
the live fill as white. Recolouring it from memory of the frame, rather than
from a disc value or a decompiled constant, would be exactly the
invented-colour failure this project's RE rules exist to rule out, and
decompiling `Hud_UpdateEnergyBar` in full (below) found no colour write onto
this widget either. So the fill draws at its authored colour: correct shape
and crop, wrong colour. Confidence 80 on the crop direction and magnitude
(`crop_vertically`'s own doc comment has the full reasoning).

## `EnergyBg` tints, `EnergyBarDelay` is wired, and `text_for` gets 2048's arms (2026-09-25)

**Decompiled `Hud_UpdateEnergyBar` in full**
(`docs/ghidra/functions/vita-2048-eu-v104/pickup-icon-uv-table.md#hud_updateenergybar---0x811957a2`,
confidence 85) rather than reading only the summary the previous pass left -
two corrections it found are now applied, not just recorded:

- **`EnergyBg`, not `EnergyBar`, is what turns red.** The function calls a
  fixed-colour draw on `EnergyBg` every tick: opaque light grey
  (`0xffa7a5a7`) normally, opaque red (`0xffff0000`) at or under 20% shield
  ([`oag_physics::damage::CRITICAL_PERCENT`]) or while the shared post-hit
  flash window is running ([`Readout::shield_flashing`], the same ~1s
  arm-on-drop timer every title already computes per tick). Wired in
  `oag_hud::dialect_2048::energy_bg_tint`.
- **`EnergyBarDelay` is a lagging trail, not a flash.** It gets the same
  vertical crop `EnergyBar` does, fed an exponentially-smoothed fraction
  (`lagging += (target - lagging) * 0.1` every tick, where `target` resolves
  to the current shield fraction on every path through the branch that sets
  it - so this is a plain one-pole low-pass toward the instant value, not a
  filter that only runs on a drop) rather than the raw one. Wired in
  `oag_hud::dialect_2048::vertical_bar_fraction` and
  `crate::race::Race::advance_energy_bar_delay`, and joins `ALWAYS_ON` (six
  names now).

**Checked live**, not only against the decompile:
`just play 2048 --race --mode single_race --no-audio --hold cross,right`
at increasing tick counts reads the shield silhouette grey at 100%/97%/82%/34%
and solid red at 15%; the 97% and 82% frames (both just after a wall hit,
neither at or under the critical floor) show a thin red sliver at the very
tip of the silhouette - `EnergyBg` peeking above `EnergyBar`'s crop, tinted
red by the still-running post-hit flash rather than the threshold, exactly
the second OR-branch the decompile names. `EnergyBarDelay`'s own crop is
pinned by `crates/raceplay/src/tests/energy_bar_delay.rs` (it reads
*above* `Readout::shield_fraction()` for a few ticks after a scripted drop,
then converges) rather than a screenshot: no capture in this pass landed on
the exact tick after a hit that would show it trailing visibly above
`EnergyBar` in a still image.

**`text_for` gained 2048's own arms**, off the widgets the layout already
authors rather than a new per-title table: `Laps` (one widget for the whole
`1/3`, where Pulse/HD split `Lap`/`LapOf`/`Lap Outof` - the name does not
collide, so no flag is needed), `Position` (combined into `8/8` when the
layout authors no `Position Outof` companion - `speed_unit`'s own
layout-absence pattern, since the *name* `Position` is shared with Pulse/HD's
split reading), and `EnergyText` (joins the existing `ShieldBarText` arm,
same format, different name). Fixing this also needed
`place_owns_the_anchor` itself corrected: it used to read "the layout
authors a `Position` widget" as "the two anchors coincide", true by
construction on Pulse's own `Arcade_HUD.xml` but false on 2048's, whose
`TotalTime` (`145, 70`) and `Position` (`945, 30`) sit in different corners
and draw at once - the presence-only version hid `TotalTime` on every 2048
race with a field, which no frame shows. It now checks the two widgets'
resolved `x`/`y` actually coincide (within half a pixel) rather than merely
existing. Checked live: `just play 2048 --race --mode single_race --no-audio
--ticks 60 --screenshot` reads `LAP 1/3`, `TOTAL 0.01.0`/`CURRENT 0.01.0`,
`POS 8/8` and `100%` together, matching `11-load-8.png`'s layout exactly
(bar the `XP`/`OBJECTIVE` rows and Zone's text, still unwired below).

  draws inside it, UV-rewritten per weapon from a table read straight off
  `eboot.elf`, centred in `PickupBgFrame`'s own rect at its native 85x86
  size. Checked against `50-r4-20.png` (Rocket) and visually against four
  more weapons (Missile, Shield, Quake, and the authored default which turned
  out to be Cannon) - `just play 2048 --race --give <weapon>`, every one
  crops to a distinct, correctly-shaped, correctly-placed icon.
  **Still not wired**: the top-centre grant announcement (no time-since-grant
  state exists on `Readout` to key it off) and its `PickupText` caption, and
  the runtime colour of anything drawn (icon and frame both keep their
  authored white - `oag_pulse::hud`'s colour-coding finding does not carry
  over, and this pass found no evidence either way for 2048).
